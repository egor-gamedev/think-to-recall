**[S1.0] Пользователь:**

Привет. У нас семейное хозяйство под Липецком, две теплицы из поликарбоната, не отапливаются. В первой теплице томаты в грунте, там две зоны полива — Z1 и Z2. Во второй огурцы в кокосовых матах, зоны Z3 и Z4. Хочу автоматизировать полив и видеть температуру и влажность. Паять умею, ESP32 в руках держал, Linux — на уровне «поставить и чтоб работало». **[S1.1] Ассистент:**

Хорошая задача, и её удобно делить на слои — тогда каждый можно менять, не трогая остальные:

1. **Датчиковые узлы** — ESP32 в каждой теплице: температура и влажность воздуха, влажность почвы по зонам.
2. **Транспорт** — MQTT: узлы публикуют показания, сервер подписан. Брокер маленький, работает на чём угодно.
3. **Сервер** — одноплатник в доме: брокер, логика полива, хранение истории, графики.
4. **Исполнительная часть** — клапаны на зонах и то, что ими щёлкает.

Чтобы не переделывать, сразу определитесь с тремя вещами:

- **Где решается, когда поливать.** Лучше на сервере: логику там проще менять и логировать, а узлы остаются «тупыми» — мерят и выполняют команды.
- **Чем открываются клапаны** — напряжение, нормально закрытые или открытые, сколько их.
- **Откуда вода** — давление и производительность определяют, сколько зон можно открыть сразу и какие клапаны вообще подойдут (многим соленоидным нужен минимальный перепад давления).

И пара вопросов: что уже куплено и какое расстояние от дома до теплиц?

**[S1.2] Пользователь:**

Сервер — Raspberry Pi 4 на 4 ГБ, уже есть, стоит в доме. На нём будет Mosquitto и свой сервис полива на Python, poliv.py, под systemd. Клапаны купил: четыре соленоидных клапана на 24 В переменного тока, нормально закрытые. Хочу, чтобы все четыре переключал один узел полива — ESP32 с 4-канальным реле в теплице №1, а к клапанам второй теплицы протяну провод, там метров 35. От дома до первой метров 40.

**[S1.3] Ассистент:**

Схема рабочая. По узлу полива несколько вещей, которые лучше сделать сразу.

**Питание клапанов.** Нужен трансформатор 220 → 24 В AC, мощность — по пусковому току. Типичный клапан берёт 0,3–0,4 А при включении и ~0,2 А удержания; на четыре клапана с запасом хватит 20–30 ВА. Держите трансформатор в отдельной коробке, не рядом с ESP32.

**Провод на 35 м.** На 24 В AC при 0,4 А падение заметное, но терпимое. Возьмите 2×1,0 мм² (лучше 1,5) — это примерно 1,2 В потерь туда-обратно при пуске. Если будете одновременно открывать два клапана второй теплицы по одному проводу — считайте ток вдвое. Общий провод (COM) можно один на два клапана, плюс по отдельной жиле на каждый клапан.

**Реле.** Модуль на 4 канала с оптронами, управление уровнем, который ESP32 выдаёт при загрузке, должен держать реле *выключенным*. Многие модули активны по низкому уровню — тогда при старте пины в неопределённом состоянии могут на мгновение открыть клапан. Решение: пины без «стяжек» при загрузке и явная инициализация в `setup()` первым делом.

**Индуктивная нагрузка.** Клапан — катушка; на AC ставьте RC-снаббер (100 Ом + 0,1 мкФ / 630 В) или варистор параллельно катушке — контакты реле проживут дольше, и помехи не будут перезагружать ESP32.

Пины под реле я бы взял такие:

```cpp
// узел полива, теплица №1
const int RELAY_PINS[4] = {16, 17, 18, 19};   // Z1, Z2, Z3, Z4
const bool RELAY_ON = LOW;                    // модуль активен по низкому уровню

void setup() {
  for (int i = 0; i < 4; i++) {
    digitalWrite(RELAY_PINS[i], !RELAY_ON);   // сначала уровень «выключено»
    pinMode(RELAY_PINS[i], OUTPUT);
  }
  // ... дальше Wi-Fi и MQTT
}
```

Избегайте пинов 0, 2, 5, 12, 15 — это strapping-пины, от их уровня зависит режим загрузки.

**[S1.5] Ассистент:**

**Почва — только на ADC1.** У ESP32 два АЦП, и ADC2 (пины 0, 2, 4, 12–15, 25–27) не работает, пока включён Wi-Fi. Для аналоговых датчиков берите ADC1: GPIO 32, 33, 34, 35, 36, 39. Пины 34–39 — только вход, без подтяжек, для датчика это как раз нормально.

```cpp
const int SOIL_PINS[2] = {34, 35};   // две зоны на узел
analogSetPinAttenuation(34, ADC_11db);  // диапазон до ~3,1 В
analogSetPinAttenuation(35, ADC_11db);
```

**Ёмкостный v1.2.** У этих плат два известных подвоха:
- На части партий нет стабилизатора или стоит не тот таймер — показания плавают от напряжения питания. Питайте от стабильных 3,3 В и проверьте, что на выходе при сухом датчике не больше ~3 В.
- Край платы и разрезанный текстолит впитывают влагу, датчик «уезжает» за сезон. Покройте края и электронику лаком или термоусадкой, в грунт — только до линии.

Калибровать придётся самим: значение в сухом воздухе и в стакане воды, потом линейно в проценты.

**SHT31 на 1,5 м I²C.** Для I²C это уже прилично, но при 100 кГц и подтяжках 4,7 кОм обычно работает. Витая пара (SDA с землёй, SCL с землёй) и экранированный кабель помогут. Сам датчик — в радиационном экране (белые тарелки или самодельный из пластиковых мисок), иначе на солнце покажет +50 там, где воздух +32.

**[S1.7] Ассистент:**

Для старта — самое то. Удобно, если узел полива умеет команду «открыть зону на N секунд» и сам закрывает по таймеру: тогда cron шлёт одно сообщение и не обязан следить за закрытием.

Команды узлу пусть приходят в топик на каждую зону:

```
poliv/z1/set   payload: 1200   (секунды)
poliv/z2/set   ...
```

На узле:

```cpp
unsigned long closeAt[4] = {0, 0, 0, 0};

void onMessage(char* topic, byte* payload, unsigned int len) {
  int zone = topic[6] - '1';                 // "poliv/zN/set"
  if (zone < 0 || zone > 3) return;
  long sec = atol(String((char*)payload).substring(0, len).c_str());
  if (sec > 0) {
    digitalWrite(RELAY_PINS[zone], RELAY_ON);
    closeAt[zone] = millis() + sec * 1000UL;
  } else {
    digitalWrite(RELAY_PINS[zone], !RELAY_ON);
    closeAt[zone] = 0;
  }
}

void loop() {
  mqtt.loop();
  for (int i = 0; i < 4; i++)
    if (closeAt[i] && (long)(millis() - closeAt[i]) >= 0) {
      digitalWrite(RELAY_PINS[i], !RELAY_ON);
      closeAt[i] = 0;
    }
}
```

На Pi в crontab пользователя (`crontab -e`):

```cron
0 7,19 * * * /usr/bin/mosquitto_pub -h localhost -t poliv/z1/set -m 1200
0 7,19 * * * /usr/bin/mosquitto_pub -h localhost -t poliv/z2/set -m 1200
0 7,19 * * * /usr/bin/mosquitto_pub -h localhost -t poliv/z3/set -m 1200
0 7,19 * * * /usr/bin/mosquitto_pub -h localhost -t poliv/z4/set -m 1200
```

Потом, когда появится poliv.py, cron можно будет заменить на его собственный планировщик или оставить cron вызывать сам скрипт — дело вкуса.

1. **Стенд на столе.** Узел, реле, вместо клапанов — лампочки или просто слушайте щелчки; трансформатор пока не подключайте.

**[S1.11] Ассистент:**

Для работы системы интернет не нужен: узлы, брокер и poliv.py общаются внутри вашей локальной сети. Интернет понадобится для:

- установки и обновления пакетов (`apt`), прошивок, библиотек;
- удалённого доступа, если захотите смотреть из города;
- уведомлений наружу, если будут.

Сама система трафика почти не тратит. Съесть лимит может только фоновая служба:

```bash
# отключить автоматические обновления, обновлять руками, когда нужно
sudo systemctl disable --now apt-daily.timer apt-daily-upgrade.timer
```

И не ставьте ничего, что синхронизирует бэкапы в облако без вашего ведома. С серым IP напрямую из интернета к Pi не подключиться — для удалённого доступа понадобится туннель или VPN, но это можно решить позже.

**[S2.9] Ассистент:**

Вот основа. Без `delay()` в цикле, с неблокирующим переподключением — чтобы узел не зависал, если брокер перезагружается.

```cpp
#include <WiFi.h>
#include <PubSubClient.h>
#include <ArduinoJson.h>
#include <Adafruit_SHT31.h>
#include "secrets.h"

WiFiClient net;
PubSubClient mqtt(net);
Adafruit_SHT31 sht;
const int SOIL[2] = {34, 35};
const int ZONES[2] = {ZONE_A, ZONE_B};
char nodeTopic[40];
unsigned long lastSend = 0, lastTry = 0;

void publish(const char* topic, float v) {
  JsonDocument doc;
  doc["v"] = v;
  doc["ts"] = (long)time(nullptr);
  char buf[64];
  serializeJson(doc, buf);
  mqtt.publish(topic, buf);
}

void ensureMqtt() {
  if (mqtt.connected() || millis() - lastTry < 5000) return;
  lastTry = millis();
  mqtt.connect(NODE_ID, MQTT_USER, MQTT_PASS, nodeTopic, 1, true, "offline");
  if (mqtt.connected()) mqtt.publish(nodeTopic, "online", true);
}

void setup() {
  snprintf(nodeTopic, sizeof nodeTopic, "teplica/%d/node/%s", TEPLICA, NODE_ID);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  configTime(3 * 3600, 0, "pool.ntp.org");
  mqtt.setServer(MQTT_HOST, 1883);
  sht.begin(0x44);
}

void loop() {
  ensureMqtt();
  mqtt.loop();
  if (millis() - lastSend < 30000 || time(nullptr) < 1700000000) return;
  lastSend = millis();
  char t[40];
  snprintf(t, sizeof t, "teplica/%d/air/temp", TEPLICA); publish(t, sht.readTemperature());
  snprintf(t, sizeof t, "teplica/%d/air/hum", TEPLICA);  publish(t, sht.readHumidity());
  for (int i = 0; i < 2; i++) {
    snprintf(t, sizeof t, "teplica/%d/z%d/soil", TEPLICA, ZONES[i]);
    publish(t, analogRead(SOIL[i]));     // пока сырые отсчёты, проценты после калибровки
  }
}
```

`NODE_ID`, `MQTT_HOST` и прочее — из `secrets.h` и флагов сборки. Почву пока отправляем сырыми отсчётами АЦП: калибровку удобнее сделать, когда датчики уже стоят в грунте.

**[S3.1] Ассистент:**

Линейно между двумя точками, с ограничением на края:

```cpp
const int RAW_DRY = 2800, RAW_WET = 1250;

float soilPercent(int raw) {
  float p = 100.0f * (RAW_DRY - raw) / (RAW_DRY - RAW_WET);
  return constrain(p, 0.0f, 100.0f);
}
```

Это «проценты шкалы датчика», а не объёмная влажность почвы — для решения «поливать или нет» этого достаточно, главное — одинаково для всех зон. Хорошо бы откалибровать каждый датчик отдельно: разброс между экземплярами v1.2 бывает 100–200 отсчётов.

Скачки ±40 — это шум АЦП ESP32, он у него заметный. Лечится медианой из нескольких замеров:

```cpp
int readSoilRaw(int pin) {
  int s[9];
  for (int i = 0; i < 9; i++) { s[i] = analogRead(pin); delay(5); }
  std::sort(s, s + 9);
  return s[4];               // медиана
}
```

Ещё лучше — `analogReadMilliVolts()`: она использует заводскую калибровку АЦП конкретного чипа, тогда калибровочные точки переносимы между узлами.

- **Минимальная пауза** между поливами одной зоны — влага доходит до датчика не сразу, и без паузы можно перелить.

```python
# poliv.py (фрагмент)
import json, time
import paho.mqtt.client as mqtt

LOW, HIGH = 30.0, 45.0
STALE = 180          # с
MIN_PAUSE = 2 * 3600 # с между поливами одной зоны
MAX_OPEN = 3600      # с — верхняя граница для узла

state = {z: {"soil": None, "seen": 0, "open": False, "last": 0} for z in (1, 2, 3, 4)}

def on_message(cl, ud, msg):
    parts = msg.topic.split("/")             # teplica/1/z2/soil
    if len(parts) == 4 and parts[3] == "soil":
        z = int(parts[2][1:])
        state[z]["soil"] = json.loads(msg.payload)["v"]
        state[z]["seen"] = time.time()
        decide(cl, z)

def decide(cl, z):
    s, now = state[z], time.time()
    if now - s["seen"] > STALE:
        return
    if not s["open"] and s["soil"] < LOW and now - s["last"] > MIN_PAUSE:
        cl.publish(f"poliv/z{z}/set", MAX_OPEN)
        s["open"], s["last"] = True, now
    elif s["open"] and s["soil"] >= HIGH:
        cl.publish(f"poliv/z{z}/set", 0)
        s["open"] = False
```

Узлы теперь шлют проценты, поэтому в `on_message` они приходят уже готовыми.

Геркон дребезжит, поэтому прерывание с антидребезгом:

```cpp
const int METER_PIN = 27;
volatile uint32_t pulses = 0;
volatile uint32_t lastPulseUs = 0;

void IRAM_ATTR onPulse() {
  uint32_t now = micros();
  if (now - lastPulseUs > 200000) {   // 200 мс: при 10 л/имп быстрее не бывает
    pulses++;
    lastPulseUs = now;
  }
}

void setup() {
  pinMode(METER_PIN, INPUT);
  attachInterrupt(digitalPinToInterrupt(METER_PIN), onPulse, FALLING);
}
```

Публикуйте нарастающий счётчик, а не «литры за период» — если сообщение потеряется, разница между соседними значениями всё равно даст верный расход. Счётчик держите в RTC-памяти ESP32 (`RTC_NOINIT_ATTR`), чтобы он не обнулялся при программной перезагрузке.

```cpp
#include <WiFi.h>
#include <esp_wifi.h>

uint8_t GW_MAC[] = {0x24, 0x6F, 0x28, 0xAA, 0xBB, 0xCC};  // MAC шлюза
const uint8_t CHANNEL = 6;

struct __attribute__((packed)) Pkt {
  uint8_t teplica, zoneA, zoneB;
  float temp, hum, soilA, soilB;
};

void setup() {
  WiFi.mode(WIFI_STA);
  esp_wifi_set_channel(CHANNEL, WIFI_SECOND_CHAN_NONE);
  esp_now_init();
  esp_now_peer_info_t peer = {};
  memcpy(peer.peer_addr, GW_MAC, 6);
  peer.channel = CHANNEL;
  esp_now_add_peer(&peer);
  sht.begin(0x44);
}

void loop() {
  Pkt p = {2, 3, 4, sht.readTemperature(), sht.readHumidity(),
           soilPercent(readSoilRaw(34)), soilPercent(readSoilRaw(35))};
  esp_now_send(GW_MAC, (uint8_t*)&p, sizeof p);

}
```

Новый logger.py — пишет пачками раз в 10 секунд, теги для теплицы и места, поле `v`:

```python
# logger.py (InfluxDB 1.8)
import json, time, threading
import paho.mqtt.client as mqtt
from influxdb import InfluxDBClient

db = InfluxDBClient("localhost", 8086, database="teplica")
buf, lock = [], threading.Lock()

def on_message(cl, ud, msg):
    _, n, place, sensor = msg.topic.split("/")
    if place == "node":
        return
    d = json.loads(msg.payload)
    with lock:
        buf.append({"measurement": sensor,
                    "tags": {"teplica": n, "place": place},
                    "time": int(d["ts"]),
                    "fields": {"v": float(d["v"])}})

def flusher():
    while True:
        time.sleep(10)
        with lock:
            batch, buf[:] = list(buf), []
        if batch:
            db.write_points(batch, time_precision="s")

threading.Thread(target=flusher, daemon=True).start()
```

**Приёмник на Pi** — небольшой сервис `lora-rx` на Python (библиотека `LoRaRF`), который разбирает пакет и публикует в те же топики, что раньше слал шлюз:

```python
import struct, time, json
from LoRaRF import SX127x
import paho.mqtt.client as mqtt

FMT = "<BBBBhhhh"
lora = SX127x()
lora.begin(0, 0, 25, 24)            # bus, cs, reset, irq
lora.setFrequency(433_500_000)
lora.setLoRaModulation(10, 125000, 5)
lora.setRxGain(lora.RX_GAIN_BOOSTED, lora.RX_GAIN_AUTO)

cl = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, "lora-rx")
cl.username_pw_set("t2_sens", open("/etc/teplica/t2.pass").read().strip())
cl.connect("localhost", 1883); cl.loop_start()

def pub(topic, v):
    cl.publish(topic, json.dumps({"v": v, "ts": int(time.time())}))

while True:
    lora.request(); lora.wait()
    raw = bytes(lora.read() for _ in range(lora.available()))
    if len(raw) != struct.calcsize(FMT):
        continue
    n, za, zb, seq, t, h, sa, sb = struct.unpack(FMT, raw)
    pub(f"teplica/{n}/air/temp", t / 10); pub(f"teplica/{n}/air/hum", h / 10)
    pub(f"teplica/{n}/z{za}/soil", sa / 10); pub(f"teplica/{n}/z{zb}/soil", sb / 10)
```

Поле `seq` позволяет считать потерянные пакеты: разрыв в номерах — пропуск. Добавьте в Grafana RSSI (`lora.packetRssi()`) — по нему сразу видно, ухудшилась ли связь.
