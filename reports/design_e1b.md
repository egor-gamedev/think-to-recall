## План прогона на Kaggle

- **Тестируемая модель:** Qwen2.5-7B-Instruct в 4 бита (AWQ) на vLLM, Kaggle T4×2, искусственный лимит контекста 8k.
- **Загрузка** одинакова для всех вариантов: диалог подаётся по репликам. При переполнении старая часть сжимается в резюме **один раз** (та же Qwen, температура 0, один промпт), и результат переиспользуется всеми вариантами — различие только в памяти.
- **Вопросы** задаются по порядку в том же чате; ответы модели входят в историю, сжатие продолжается.
- **Варианты:** 1) резюме; 2) резюме + RAG по истории (эмбеддинги, тот же бюджет токенов); 3) резюме + ctxgraph, `auto_depth = 1`; 4) резюме + меню ctxgraph и раскрытие по выбору; 5) случайное меню того же размера. Подсказки помечены как «воспоминания, не требования».
- **Судья:** сильная модель не из семейства Qwen, проверка по спискам из скелета. Два судьи на 20% ответов.
- На Kaggle бесплатно и ответы, и сжатие. Платно только судья через timeweb: ≈ 15 проходов вопросов × 5 вариантов × 3 проекта = 225 оценок.

### Открытый вопрос дизайна: чем ctxgraph помогает именно «памяти проекта»

В E1 меню строилось из **внешних** словарей (WordNet, Викиданные) — для памяти проекта они почти ничего
не дают. Здесь нужен слой «из прошлого разговора»: фрагменты и сущности загрузочного диалога, связанные
с вопросом через общие сущности, их соседи по совместной встречаемости (слот «опыт» — по разметке Егора
раунда 3 он проходит порог 60%) и устаревшие версии фактов. Предлагаю в варианте 3 давать: якорные сущности
вопроса → фрагменты прошлого разговора с ними (кратко) → связанные сущности, плюс 1–2 подсказки из внешних
словарей. Иначе граф проверяется не на той задаче. Нужно согласие Егора.

## Память вариантов: проверка на реальных блоках (2026-10-21)

Блоки собраны для crypto-wallet при лимите 6k, токенизатор Qwen2.5, эмбеддинги model2vec.

- **Рёбра «заменяет».** Было: маркеры вроде «теперь» срабатывали почти на каждой реплике, и V6 помечал как «позже заменено» почти всё. Стало:
  - ребро ставится только от реплики пользователя с явным словом смены решения (отказ…, передумал, ушли с, переходим на, больше не, вместо, …);
  - ребро ведёт к одной более ранней реплике пользователя с наибольшим score = Σ idf общих нечастых сущностей + 5·cos.
- **Качество рёбер против эталона скелетов** (8 смен решений, полная загрузка трёх проектов): верных 5 из 12 (точность 0,42), найдено 5 из 8 (полнота 0,62).
  - Пропуски: смена без слова-маркера (F04b, G13b «с января») и смена, где старая реплика не делит сущностей с новой (F01b, «веба не будет»).
  - Часть «ложных» рёбер — реальные смены, которых нет в эталоне (cron → Celery, unittest → pytest).
  - Правило зафиксировано до прогона; по эталону больше не подгоняем.
- **Якоря V3/V4/V6.** Сущности, которые встречаются больше чем в max(3; 15 % реплик архива), не берутся ни в якоря, ни в основание для рёбер. Раньше якорями становились «пользователь», «схема».
- **V2 с model2vec слабый** (Q04 Solana: нужная реплика не в топе). Для честного сравнения на Kaggle V2 и V6 используют один и тот же более сильный эмбеддер — multilingual-e5-base (предложение, в пре-регистрацию).
