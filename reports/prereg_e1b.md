Может ли память по собственной истории разговора — граф (V3, V4) или гибрид RAG + граф (V6) — помочь маленькой модели понять проект из накопленного контекста? Сравнение идёт с:

- обычным RAG (V2);
- случайным меню той же формы (V5).

## 3. Модель и условия

- **Модель.** Qwen2.5-7B-Instruct-AWQ (4 бита), vLLM, Kaggle T4×2, температура 0. Запасной путь, если vLLM не встанет: transformers + bitsandbytes NF4. Путь выбирается один раз на весь прогон и записывается в `meta.json`.
- **Лимит контекста — 6600 токенов** (в спецификации пример — 8k). Окно истории — 3750 токенов, как в пилотах: при нём проекты сжимаются 3–6 раз, а при 8k проекты 2 и 3 сжимались бы 2–3 раза.
- **Бюджеты:** ответ 1500 (решено после пилота 2: при 900 обрывалась половина ответов), блок памяти ≤ 600, резюме ≤ 500, системный промпт 250, окно истории 3750.
- **Сжатие.** Одинаковое для всех вариантов:
  - когда окно не помещается, старшая половина уходит в резюме;
  - резюме пишет та же Qwen, одним промптом (`ctxgraph/e1b/chat.py`);
  - ушедшие реплики попадают в архив — источник памяти V2–V6.
- **Порядок вопросов.**
  - Загрузка проигрывается один раз; дальше каждый вариант идёт своей копией чата.
  - Вопросы задаются по порядку. Ответ модели остаётся в истории, поэтому возможны сжатия и между вопросами.
  - Follow-up добавляется в историю после своего вопроса.

## 4. Варианты (код: `ctxgraph/e1b/memory.py`)

Блок памяти ставится перед вопросом пользователя с пометкой «Это воспоминания и ассоциации из прошлого разговора, не требования; используй, только если относится к вопросу».

| | что в блоке |
|---|---|
| V1 | ничего (только резюме) |
| V2 | 6 ближайших по эмбеддингу реплик архива (до 110 токенов каждая) |
| V3 | граф: якоря вопроса (сущности вопроса, есть в архиве, не частые) → последнее упоминание + ассоциации (PMI > 0); auto_depth = 1 раскрывает самую частую ассоциацию |
| V4 | меню тех же якорей и ассоциаций; `expand(id)` раскрывает до 3 пунктов |
| V5 | форма V3, но ярлыки и выдержки — случайные из других проектов (seed по проект/вопрос/вариант) |
| V6 | гибрид, описание ниже |

V6 по шагам:
1. BM25 и эмбеддинги, слияние RRF, топ-8.
2. 1 шаг по графу: общая редкая сущность у трёх лучших и цепочка «заменяет».
3. Ответы модели взвешиваются ×0,6 и помечаются «сказано моделью — ниже доверие».
4. Устаревшее помечается «позже заменено».
5. В блок идут тексты 4 лучших фрагментов, остальное — ярлыками «Ещё по теме».

- **Эмбеддер V2 и V6 — общий:** multilingual-e5-base. model2vec на проверке оказался слабым для RAG, и мы не хотим ослаблять базовую линию.
- **Рёбра «заменяет»** — автоматические, правило зафиксировано. Против эталона скелетов: точность 5/12, полнота 5/8 (`reports/design_e1b.md`).
- **Размер блока.** 600 — это предел, а не обязательный размер. V3/V4/V5 бывают пустыми, если у вопроса нет якорей. В отчёт идут средние размеры блоков по вариантам.

## 5. Метрики (на каждый ответ, судья по спискам из скелета)

- **опора:** доля опорных фактов, которые ответ учёл;
- **вывод:** понял или уточнил ожидаемое (да / нет);
- **неуместный совет:** да / нет;
- **выдумка:** утверждает факт о проекте, которого не было (да / нет);
- **удержание:** в вопросе удержания использован вывод из follow-up (да / нет).

**Все метрики считаются отдельно по типам вопросов** (вспомнить / связать / менялось / уточнить) и в сумме.

## 6. Гипотезы и тесты

Тесты: McNemar по вопросам — для бинарных метрик; парный бутстреп, 10 000 повторов, — для «опоры». Уровень 0,05, двусторонние тесты, Холм внутри семейства.

**H1 — ключевая для идеи графа (указание Егора).** V6 лучше V2 по «вывод» на типах «связать» (18 вопросов) и «менялось» (15). Семейство из 2 тестов, Холм. Тот же разрез по «неуместному совету» и «опоре» — вторичный.

**H2 — успех по спецификации.** Хотя бы один из V3, V4, V6 лучше каждого из V1, V2, V5 по «вывод» на всех 54 вопросах (9 тестов, Холм) и при этом не хуже по «выдумке».
- «Не хуже» означает: доля выдумок выше, чем у сравниваемого варианта, не больше чем на 5 п.п. по верхней границе 95 % бутстреп-интервала.
- Если ctxgraph лучше только V1, но не V2, вывод — граф не даёт больше обычного RAG.

**H3 — нулевой прогноз.** На «вспомнить» разницы V6 и V2 не ожидаем. Отчёт: разность и 95 % интервал. Тест на эквивалентность не проводим — при 14 вопросах он заведомо слабый.

Всё остальное (V4 и частота вызовов `expand`, удержание, разрезы по проектам) — описательно.

**Ограничение по мощности.** При 54 вопросах McNemar замечает только крупные эффекты (порядка 25 п.п.), на подтипах из 15–18 вопросов — ещё крупнее. Неотвергнутая гипотеза означает «не показано», а не «нет эффекта».

## 7. Судья

- Код: `ctxgraph/e1b/judge.py`, промпт `JUDGE_PROMPT_VERSION = "e1b.3"`; запуск — `scripts/e1b_judge.py`.
- **Что видит судья:** все факты проекта (устаревшие помечены «заменено …»), вопрос, опорные факты, ожидаемый вывод, неуместные советы, для удержания — реплику follow-up, и ответ.
  - Вариант и блок памяти судья не видит; порядок ответов перемешан (seed 0).
- **Что возвращает (JSON):** опора по каждому опорному факту, вывод, неуместный совет, `stale` (опирается на устаревший факт как на текущий), выдумка со списком, `intrusion` (постороннее: темы не из вопроса и не из проекта) со списком, удержание.
- **Судьи — API NVIDIA (`integrate.api.nvidia.com`, бесплатно), температура 0:**
  - **основной — z-ai/glm-5.3**, на всех ответах. Медленный (рассуждения не отключаются, 1–2 мин на ответ), зато точнее держит определения рубрики;
  - **второй — nvidia/nemotron-3-ultra-550b-a55b**, на всех ответах (≈ 15 с на ответ). κ считается по всем 324 ответам, а не по 20 % — так дёшево и мощнее.
  - Kimi K2.6 недоступен для ключа, DeepSeek V4.1 Flash не отвечал (таймаут) — не используются.
- **Проверка на пилоте 2** (27 общих ответов, промпт e1b.3):

| метрика | GLM | Nemotron | согласие | κ |
|---|---|---|---|---|
| вывод | 6 | 5 | 0,96 | 0,89 |
| неуместный совет | 20 | 20 | 0,93 | 0,81 |
| опора (81 факт) | | | 0,95 | 0,85 |
| устаревшее | 1 | 2 | 0,96 | 0,65 |
| постороннее | 3 | 9 | 0,78 | 0,40 |
| выдумка | 0 | 13 | 0,52 | 0,00 |

- **Выдумка — решено после проверки судей.** Nemotron записывает в выдумку неуместные советы (шаблон логина с паролем, план интеграции Solana), хотя рубрика это прямо исключает; GLM строже. Поэтому:
  - итоговая «выдумка» = ответы, отмеченные хотя бы одним судьёй, после ручной проверки;
  - проверяющий не видит вариант;
  - правило: выдумка — только утверждение, что в проекте уже есть, решено или действует X;
  - проверяет Егор или Claude по списку `fabricated` с цитатами; кто проверял — в отчёт.
- По остальным метрикам итог — оценка основного судьи; расхождения с вторым по «вывод» показываются Егору выборочно (до 30).
- «Постороннее» — вторичная метрика, описательно. На пилоте её дают в основном V5 (случайная память чужих проектов) и V6.

## 9. Технический пилот (до утверждения, в результат не входит)

- **Состав:** crypto-wallet, Q01–Q05, все 6 вариантов, на Kaggle.
- **Проверить:**
  - модель встаёт на T4;
  - сжатия идут;
  - блоки памяти по бюджету;
  - `expand` в V4 разбирается;
  - ответы не обрываются на 900 токенах.
- Судья на пилоте — 30 ответов пилота 2, через NVIDIA (см. §7).

### 9.1. Пилот 1 (2026-10-21, vLLM офлайн, последовательно) — что увидели

- vLLM 0.32 на T4×2 работает (AWQ, TP=2), запасной путь не понадобился.
- Сжатия: 6 при загрузке, ещё 2 за 5 вопросов; блоки памяти ≤ 572 токенов.
- **Обрывы:** 14 из 30 ответов упёрлись в 900 токенов — модель не держит «до 300 слов».
  - Решено после пилота: в системном промпте «до 200 слов», лимит ответа остаётся 900.
  - В записи теперь есть `finish_reason`; доля обрывов идёт в отчёт.
- **V4:** `expand` не вызван ни разу (0 из 5), как и ожидалось для 7B. V4 фактически равен «меню без раскрытия».
- **Пустая память:** на Q01 (JWT, сущностей нет в архиве) V3/V4/V5 пусты, ответ совпадает с V1.
- **Скорость:** ≈ 50 с на вызов, 30 ответов + 18 резюме за 42 мин; полный прогон занял бы ≈ 6 ч.
  - Решено после пилота: `vllm serve` и шесть вариантов параллельно; сервер батчит запросы, память строится последовательно.
  - Проверка на заглушке: параллельный прогон даёт те же блоки памяти при повторе (90/90).
### 9.2. Пилот 2 (2026-10-22, `vllm serve`, варианты параллельно)

- 30 ответов + загрузка за 304 с (было 2493 с). Полный прогон, 270 ответов, займёт ≈ 1 ч GPU.
- **Обрывы — 16 из 30, несмотря на «до 200 слов»;** медиана ответа — 900 токенов. Qwen-7B не держит длину по инструкции. **[решить]**
  - Предложение: оставить как есть. Лимит одинаков для всех вариантов; судья оценивает то, что модель успела сказать. Доля обрывов по вариантам идёт в отчёт.
  - Альтернатива: лимит ответа 1500 при контексте 6600. Сжатий станет столько же, но вырастет время.
- `expand` снова 0 из 5.
- Сырые записи обоих пилотов — `reports/e1b/pilot1`, `reports/e1b/pilot2`.

- **Пример (V6, Q04 Solana).** В блоке первой строкой стоит «Solana обсуждали и отказались», модель всё равно расписала добавление Solana. Задача не тривиальна для 7B — риск «пола», а не потолка.

## 11. Поправка v1.1 (Егор, 2026-10-22) — судьи

Записана и закоммичена до любого анализа по вариантам. Посмотрены были только счётчики прогресса оценки (сколько ответов оценено), без сводок по вариантам.

1. **Причина — технический сбой.** GLM-5.3 на NVIDIA перегружен и не отвечает: 0 оценок из 324 за ≈ 4 ч, даже на короткий запрос нет ответа за 120 с. Решение принято без просмотра результатов по вариантам.
2. **Основной судья — nvidia/nemotron-3-ultra-550b-a55b по всем метрикам.** «Выдумка» — как в §7: ручная проверка ответов, отмеченных судьёй, вслепую к варианту.
3. **Второй судья — DeepSeek V4.1 Flash, на 20 % ответов.** Выборка — заложенная в `scripts/e1b_judge.py --sample 0.2`: детерминированная по sha256 ключа «проект|вопрос|вариант». κ с основным судьёй — в отчёт.
   - Канал — NVIDIA (`deepseek-ai/deepseek-v4.1-flash`, бесплатно). На timeweb это та же модель (`deepseek/deepseek-flash`), но на счёте 6 ₽, а нужно ≈ 20 ₽.
   - На момент записи DeepSeek на NVIDIA тоже не отвечает (таймаут 150 с). Будут повторы; если не поднимется — решение за Егором (пополнить timeweb или другой судья).
4. **GLM-5.3:** если он к концу что-то оценит, ответы сохраняются (`judge_glm.jsonl`) и идут в отчёт третьим судьёй. На выводы не влияют.
5. **Тестируемая модель — Qwen2.5-7B-Instruct-AWQ (Alibaba, семейство Qwen)**: не DeepSeek и не Nemotron.
   - Судьи из других семейств: Nemotron 3 — собственная модель NVIDIA, DeepSeek V4.1 Flash — DeepSeek, GLM — Zhipu.
   - Анализ (`scripts/analyze_e1b.py`) переключается на основного судью Nemotron.

## 13. Поправка v1.3 (Егор, 2026-10-22) — перепроверка «выдумки» с диалогом

1. **Причина — ошибка в процедуре.** И судьи, и ручная проверка сверяли ответ со списком фактов скелета, а не с самим разговором. Часть подтверждённых выдумок — реальные детали из диалога загрузки, не вошедшие в список фактов: 3'-смещение у образца F3, монорепа, CoinGecko, Prisma, «812 генов», `environment.yml`.
   - Обнаружено при разборе результатов: решение принято после того, как результаты по вариантам уже посчитаны.
2. **Процедура.** Новая отдельная сессия Claude вслепую к варианту перепроверяет 26 ответов, подтверждённых как выдумка.
   - Ей даются тексты диалогов загрузки (S1–S5, одинаковые для всех вариантов), факты и вопросы.
   - Правило §7 уточняется: выдумка — утверждение о проекте, которого нет ни в фактах, ни в диалоге загрузки, ни в вопросе, или которое им противоречит.
   - Ответы модели на более ранние вопросы прогона в пакет не входят: они разные у разных вариантов и раскрыли бы вариант. Деталь, взятая только из такого ответа, считается выдумкой.
3. **Остальные 123 из 149 проверенных** остаются 0: с более полным контекстом утверждение может только перестать быть выдумкой.
4. **Отчёт** показывает «выдумку» по v1.2 и по v1.3; итог H2 по «не хуже по выдумке» — по v1.3.
