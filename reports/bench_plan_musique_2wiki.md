# План первого чужого бенчмарка: MuSiQue и 2Wiki, Recall по абзацам (Kaggle GPU, без API)

> Статус: **план, ничего не запускалось.** Актуальная версия (варианты а–г, время, параметры) — в
> `reports/prereg_bench1.md`; этот файл — ранний набросок.

## Что меряем

- **Данные:** выпуск HippoRAG 2 (`osunlp/HippoRAG_2`, ревизия 5ec05b38de), те же 1 000 вопросов на набор и те же корпуса, что в статье.
  - MuSiQue: 11 656 абзацев, 43 693 предложения (посчитано). Лицензия CC BY 4.0.
  - 2WikiMultiHopQA: 6 119 абзацев, 23 071 предложение (посчитано). Лицензия Apache-2.0.
- **Метрика:** Recall@2 и Recall@5 **по абзацам**, как в HippoRAG 2 — доля опорных абзацев вопроса в первых k.
  - Оценка абзаца = максимум оценок его предложений.
  - Отдельно, не для сравнения — Recall по предложениям.
- **Вызовов LLM: 0** — ни на построение графа, ни на поиск. Ответы и F1 — отдельным этапом, позже.
- **С чем сравниваемся** (числа из статьи HippoRAG 2, Recall@5):

  | система | MuSiQue | 2Wiki |
  |---|---|---|
  | HippoRAG 2 | 74,7 | 90,4 |
  | NV-Embed-v2 (dense) | 69,7 | 76,5 |

  Внутренний контроль — наш dense-поиск на e5-base: та же модель эмбеддингов, что в графе. Так видно, что даёт граф сверх эмбеддингов, а не сверх более сильного энкодера.

## Варианты (все без LLM)

1. **dense:** e5-base по предложениям → абзацы.
2. **v2-PPR:** гибридный старт (dense + BM25 → RRF) → PPR по графу → абзацы.
3. **v2-PPR + переранжирование:** вариант 2 + bge-reranker-v2-m3 на GPU по top-40 предложениям.
4. **v2 + рукава из вопроса:** группы слов вопроса → мини-графы → объединение.
   - Описательно: на этапе A3 рукава из вопроса ничего не дали сверх поиска по вопросу.
   - Рукава из шагов мышления требуют LLM, поэтому идут вторым этапом.

Конфигурация замораживается в пре-регистрации; после неё параметры не меняются. Порог `min_score` в Recall не участвует: ранжирование не зависит от отсечения.

## Устройство прогона

- **Один граф на набор:** абзац = эпизод (роль `document`, заголовок + текст), предложения — фрагменты.
  - Детектор смены решения для документов выключен.
  - Граф строится один раз, затем 1 000 вопросов ищут по нему.
- **Kaggle:**
  1. Приватный датасет с кодом `ctxgraph` и данными HippoRAG 2. Ключей нет, есть проверка на `.env`, как в `e1b_kaggle_pack.py`.
  2. Ядро с GPU: построение графа → поиск → `recall.jsonl` и сводка.
  3. Результаты скачиваются через Kaggle API; локально считается отчёт.

## Оценка времени

| этап | MuSiQue | 2Wiki | на чём |
|---|---|---|---|
| извлечение spaCy | ≈ 5,5 мин | ≈ 3 мин | CPU Kaggle (в 4 процесса — ≈ 1,5 / 1 мин) |
| эмбеддинги e5-base | ≈ 1 мин | ≈ 0,5 мин | GPU (оценка 500–1 000 предл./с, проверить) |
| рёбра «синоним» (близость понятий) | **риск**, см. ниже | | GPU, блочное умножение матриц |
| поиск 1 000 вопросов (старт + PPR) | ≈ 5–10 мин | ≈ 3–6 мин | CPU (оценка; PPR по графу ~10⁵ узлов) |
| переранжирование top-40 × 1 000 | ≈ 2–3 мин | ≈ 2–3 мин | GPU (оценка 200–400 пар/с) |
| **итого** | **≈ 15–25 мин** | **≈ 10–15 мин** | одна сессия Kaggle |

На нашем CPU то же самое заняло бы ≈ 1 ч (MuSiQue) и ≈ 32 мин (2Wiki) только на построение, плюс ≈ 3,3 ч на переранжирование. Поэтому — Kaggle.

## Что доделать до прогона (код, без запусков на полных данных)

1. **Пакетный расчёт рёбер «синоним».** Сейчас каждое новое понятие сравнивается со всеми прежними на CPU. На английском корпусе это ~10⁵ понятий и ~5·10⁹ сравнений.
   - Для документов — блочный расчёт на GPU. Результат тот же, что при дозаписи: порог симметричен.
   - Тест: пакетный способ == по одному на маленьком корпусе.
2. **Раннер бенчмарка** `scripts/bench1_run.py`:
   - загрузка данных → граф → варианты 1–4 → `recall.jsonl`;
   - Recall по абзацам как в HippoRAG 2 (`2hop` / `3hop` / `4hop` — по типам вопросов MuSiQue).
3. **Ядро Kaggle и упаковка** — по образцу `kaggle/e1b`.
4. **Отладка ≤ 5 мин локально:** 50 вопросов MuSiQue с их абзацами (свой маленький корпус), CPU. Только проверка, что всё работает; выводов не делаем.
5. **Пре-регистрация:** варианты, модели с ревизиями, параметры (`synonym_thr`, `damping`, `passage_weight`, `min_content_words`, число кандидатов), метрика, сравнения, критерий.
   - Предлагаю такой критерий: v2-PPR лучше dense на e5 по Recall@5 на обоих наборах, парный бутстреп по вопросам, 95 %.

## Риски

- **Пороги подобраны на русском отладочном наборе:** `synonym_thr` = 0,965 и якорь цели. Для английских абзацев они могут не подойти. До пре-регистрации проверить распределение близостей на 2Wiki (≤ 5 мин), но **не подбирать по Recall**.
- **Взрыв числа понятий и рёбер на английском:** spaCy даёт ~24 понятия на абзац. Ограничение пар `cooccur` в предложении уже есть.
- **Несопоставимость с HippoRAG 2 по энкодеру:** у них NV-Embed-v2 (7B), у нас e5-base. Поэтому главное сравнение — с нашим dense на том же e5; цифры статьи — для ориентира.
