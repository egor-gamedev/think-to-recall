# Как устроен ctxgraph сейчас (2026-10-30, только чтение кода)

## Главное

- **В репозитории две разные реализации «графа», и они не связаны.**
  1. **Продуктовый граф** — [ctxgraph/graph.py](../ctxgraph/graph.py), [ctxgraph/store.py](../ctxgraph/store.py), MCP-сервер [ctxgraph/mcp_server.py](../ctxgraph/mcp_server.py). Это граф понятий из словарей (WordNet, RuWordNet, Викиданные) и меню соседей. Хранится в SQLite.
  2. **Память бенчмарков E1b/E1c/E1d** — [ctxgraph/e1b/memory.py](../ctxgraph/e1b/memory.py) (`Archive`). Это индекс реплик в оперативной памяти: сущности, эмбеддинги, BM25, рёбра «заменяет».
- Все цифры E1b, E1c и E1d получены на второй реализации. **Продуктовый граф ни разу не мерился на вопросах о проекте.**

### Перезаписывается ли граф целиком?

**Продуктовый граф (SQLite) — нет.**
- Всё пишется дозаписью: `INSERT … ON CONFLICT DO UPDATE` и `INSERT OR IGNORE`, файл базы не пересоздаётся.
- Три оговорки:
  - при повторной записи узла его подпись перезаписывается (`put_node`, `ON CONFLICT … SET label=excluded.label`);
  - базовый вес ребра берётся максимальный из старого и нового (`put_edge`, `base=MAX(base, excluded.base)`);
  - рёбра никогда не помечаются недействительными и не удаляются.

**Память бенчмарков — да, на каждом вопросе.**
- `runner._ask` строит `M.Archive(state.archive, encoder)` заново на каждый вопрос: сущности всех реплик, BM25, эмбеддинги (кэш энкодера спасает только от повторного кодирования), заново запускается детектор «заменяет» по всем репликам.
- На диск ничего не пишется: граф живёт только внутри одного вопроса.
- Межсессионности нет.

## 1. Что хранится

### Продуктовый граф (`store.py`, схема `SCHEMA`)

| таблица | что | атрибуты |
|---|---|---|
| `nodes` | узлы-понятия: `wn:` / `rwn:` (WordNet / RuWordNet), `wd:Q…` (Викиданные), `ent:<термин>` (термин из контекста), `exp:` (опыт) | `label`, `source`, `lang`, `meta`; **нет времени и автора** |
| `edges` | рёбра «соседи из словаря» и «привязка» термина к узлу | `rel`, `source`, `slot` (deeper / side / assoc / experience / far), `base` (вес из источника), `bonus` (закрепление, затухает с полураспадом 30 дней), `uses`, `expansions`, `shown`, `created`, `provenance`; **нет времени окончания и статуса «недействительна»** |
| `fragments` | фрагменты контекста (абзац, сообщение, блок кода) | `kind`, `source` (`msg:3:user`), `label`, `text` (только для message / paragraph / statement / tool_call; у файлов и кода текста нет), `session`, `ts` |
| `mentions` | фрагмент ↔ сущность | `entity`, `kind`, `session`, `surface` |
| `shortcuts` | сокращения пути «якорь → цель через узел» | контекст и его вектор, `weight`, `uses` |
| `cache`, `events` | кэш ответов Викиданных; журнал menu / expand / used | |

- Файл лежит в `.cache/graph.sqlite` ([ctxgraph/\_\_init\_\_.py](../ctxgraph/__init__.py)).
- Важно: **фрагменты не являются узлами графа.** Они лежат отдельной таблицей и связаны с понятиями только через `mentions`. Рёбра между понятиями берутся из словарей, а не из разговора.

### Память бенчмарков (`e1b/memory.py`, `Archive`)

- **Узлы:** реплики архива (`Turn`: id, роль, текст, источник реплики — загрузка / вопрос / ответ модели / follow-up).
- **Сущности реплики** (`ents`) — через `extract_entities` и фильтр `is_concept`.
- **Рёбра:**
  - неявные, «общая сущность» (`by_ent`);
  - явные, «заменяет» (`replaces`: поздняя реплика → ранняя).
- Плюс эмбеддинги e5 (первые 200 токенов реплики) и BM25 по леммам.
- **Время** — только порядок реплик (`order`).

## 2. Как строится

**Извлечение без генеративной модели** ([ctxgraph/ingest.py](../ctxgraph/ingest.py)):
- регулярки для URL, путей, дат, величин, кодов ошибок;
- идентификаторы (snake_case / camelCase, `def` / `class`, `import`);
- ключевые фразы YAKE;
- леммы pymorphy3.

**Привязка термина к узлу словаря** (`Engine._link_term`) — по близости описания смысла к фрагменту (model2vec), с порогами для технических фрагментов.

**Связи между понятиями** берутся из соседей узла в словаре (`Source.neighbors`) лениво, в момент построения меню.

**Из разговора связей нет**, кроме:
- совместной встречаемости в одном фрагменте — источник «опыт», [sources/experience.py](../ctxgraph/sources/experience.py) (PMI по сессиям);
- в бенчмарк-памяти — «общей сущности».

**«Заменяет»:**
- в продуктовом графе — **нет**;
- в бенчмарк-памяти — детектор v2 [ctxgraph/e1b/replaces.py](../ctxgraph/e1b/replaces.py): явная фраза смены решения → вырезается старое X → самая ранняя реплика пользователя с X. Точность 9/10 по разметке Егора, полнота около 8/29.

**Фильтр приватности** ([ctxgraph/privacy.py](../ctxgraph/privacy.py)):
- регулярки для ключей, токенов, JWT, паролей в присваиваниях, email, телефонов, карт, длинных hex / base64;
- в продуктовом графе применяется до записи (`ingest._make`);
- **в бенчмарк-памяти не применяется вообще** — `Archive` берёт текст реплик как есть;
- имён, адресов и названий организаций не ловит (NER нет).

## 3. Обновление

**Продуктовый граф:**
- `Engine.observe(context)` дописывает фрагменты и упоминания (`INSERT OR IGNORE`, id фрагмента — хэш источника и текста);
- `Engine.menu` дописывает узлы и рёбра, до которых дошёл;
- `mark_used` увеличивает `bonus` и записывает сокращение.
- **При смене решения ничего не происходит:** старые связи и фрагменты остаются как были, без отметки.

**Память бенчмарков:**
- реплика попадает в архив, когда её вытесняет сжатие окна ([ctxgraph/e1b/chat.py](../ctxgraph/e1b/chat.py), `compress_if_needed`: старшая половина окна уходит в резюме и в архив);
- граф собирается заново перед каждым вопросом (см. выше);
- старое при смене решения остаётся, но получает пометку «позже заменено», если детектор поймал смену.

## 4. Поиск и подача в промпт

**Бенчмарк-путь, вариант V6** — от вопроса до текста в контексте:
1. `runner._ask` при необходимости сжимает окно и строит `Archive` из архива.
2. `v6_candidates`:
   - BM25 и эмбеддинги вопроса → RRF → top-8 реплик;
   - шаг по графу: у трёх лучших берутся по две самые редкие сущности и последние две реплики с ними;
   - для заменённых добавляются заменившие реплики;
   - вес: слова модели × 0,6.
3. `v6_hybrid`: 4 лучшие реплики — выдержкой до 110 токенов, остальные — ярлыками по 12 токенов. Заголовок «воспоминания, не требования», бюджет 600 токенов.
4. `Session.messages`: система + резюме → окно последних реплик → блок памяти, «---», вопрос.

**Новые слои E1d** — код есть, на модели не прогонялся:
- рукава `v9.py` и рукава-фразы;
- отбор по предложениям с cross-encoder ([ctxgraph/e1b/selection.py](../ctxgraph/e1b/selection.py));
- протокол шагов [ctxgraph/e1b/steps.py](../ctxgraph/e1b/steps.py).

**Продуктовый путь** (MCP `menu`):
1. `ingest(context)` → по каждому фрагменту — кандидаты-якоря (YAKE, редкость, близость к блоку).
2. Привязка к словарям → рукав: соседи по слотам «глубже / в сторону / ассоциации / опыт / далёкое».
3. Пересечения рукавов.
4. Текстовое меню с id (`menu.render`). Модель вызывает `expand(id)` и `mark_used(id)`.

## 5. Расхождения с `CONTEXT_GRAPH.md`

| в концепции | на деле |
|---|---|
| движок раскладывает **рабочий контекст** в граф: узлы — фрагменты, факты, мысли; рёбра — связи между ними | в продукте узлы — понятия словарей, фрагменты не узлы; связей из контекста почти нет (только совместная встречаемость) |
| происхождение у каждого узла и ребра | у рёбер — строка `provenance`; у узлов только `source`; у бенчмарк-памяти — только id реплики |
| типы связей с логическими свойствами (SIL), правила распространения по нетранзитивным связям | не реализовано |
| статусы «из источника / выведено / гипотеза» | не реализовано |
| меню по выбору модели (V4 / V7) | реализовано; на бенчмарках проиграло авто-подаче (E1c: V7 хуже V6, −6 п.п., p = 0,081) |
| закрепление за пользу, квота исследования, медленное затухание | реализовано в продукте (`mark_used`, слот «далёкое», полураспад); в бенчмарках не использовалось |
| — | Multi-user features are out of scope of this repository. |
| рукава мышления из шагов модели, периферия, затухание 0,5^d | код E1d есть, на модели не прогонялся |
| межсессионный граф | в продукте — да (одна SQLite, сессии в `fragments` / `mentions`); в бенчмарк-памяти — нет |
| граф не перестраивается | продукт — не перестраивается; бенчмарк-память — перестраивается на каждый вопрос |

## 6. Известные ошибки и подозрения

1. **Мерили не то, что продаём.** Выводы E1b–E1d относятся к `e1b/memory.py`, а не к продуктовому графу.
2. **Перестройка на каждый вопрос** в бенчмарк-пути. При росте истории это O(n) на вопрос, и детектор «заменяет» пересчитывается по всем репликам.
3. **Смена решения не отражается в структуре:**
   - в продукте никак;
   - в бенчмарке — только пометкой при пойманной смене;
   - полнота детектора около 28 % (8/29), поэтому большинство смен не видно.
4. **Нет фильтра приватности** в бенчмарк-памяти. Регулярки продукта не ловят имена, адреса и организации.
5. **Эмбеддинг реплики — первые 200 токенов.** Факт в конце длинной реплики для плотного поиска невидим. По этой же причине старая метрика полноты засчитывала начало реплики без факта — урок V9-q3.
6. **«Только сущности» теряют контекст.** На этапе A рукава-сущности из вопроса не дали ничего сверх поиска по всему вопросу при равном размере пула. Это совпадает с выводом HippoRAG 2.
7. **Две кодовые базы с похожими, но разными функциями** — извлечение и рукава в `graph.py` против `v9.py` / `sleeves.py`. Риск чинить не там.
8. **Недетерминизм** при равных весах был, исправлен (570adb3), тест есть. Цифры E1c получены до исправления.
9. Multi-user features are out of scope of this repository.
10. **Узел не хранит время и автора;** `put_node` при повторной записи молча меняет подпись.
