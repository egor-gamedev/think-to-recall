## 1. Вопрос и главное сравнение

**Вопрос:** даёт ли граф v2 (персонализированный PageRank по графу понятий и предложений) прирост полноты поиска над dense-поиском на **том же** энкодере.

- **Главное сравнение — прирост графа над нашим dense: (в) − (а), Recall@5 по абзацам**, отдельно на MuSiQue и на 2Wiki.
- **Критерий успеха:** нижняя граница 95 % интервала парного бутстрепа для (в) − (а) по Recall@5 **выше 0 на обоих наборах**.
  - Успех требует выполнения обоих условий (тест «пересечение–объединение»), поэтому поправка на множественность не нужна.
- **Сопоставление с HippoRAG 2 — описательно, не критерий.** Их прирост над NV-Embed-v2 по Recall@5: **+5,0** на MuSiQue (74,7 против 69,7) и **+13,9** на 2Wiki (90,4 против 76,5).
  - У них энкодер NV-Embed-v2 на 7B параметров, у нас e5-base. Поэтому сравниваем приросты над своим dense, а не абсолютные числа.
  - Ещё одно отличие: у HippoRAG 2 тройки строит LLM, у нас — правила, 0 вызовов LLM.

## 3. Варианты (без вызовов LLM)

Все варианты ранжируют абзацы корпуса. Оценка абзаца = максимум оценок его предложений.

| вариант | что делает |
|---|---|
| **(а) dense** | e5-base: вопрос с префиксом `query:`, предложения с префиксом `passage:`; косинус; top-500 предложений → абзацы |
| **(б) dense + BM25 + RRF** | (а) + BM25 по леммам (SQLite FTS5), top-500; слияние RRF, k = 60. Недобранные абзацы — в порядке (а) |
| **(в) граф v2 + PPR** | старт: предложения из (б) (top-30) и понятия вопроса (вес 1/число предложений с понятием, HippoRAG 1) → персонализированный PageRank по графу (понятия, предложения; рёбра `contains`, `cooccur`, `synonym`, `subphrase`, `next`) → оценка предложений. Недостигнутые абзацы — в порядке (б) |
| **(г) (в) + переранжирование** | top-40 предложений из (в) → bge-reranker-v2-m3 (fp32, GPU; запрос — вопрос). Остальные абзацы — в порядке (в) |

- Рукава мышления здесь **не проверяются**: им нужны шаги модели, это отдельный прогон позже.
- Абзац записывается в граф как эпизод с ролью `document` (заголовок + текст). Детектор смены решения для документов не запускается. Граф строится один раз на набор, дальше только дозаписью.

## 5. Метрики и анализ

- **Recall@k вопроса** = |опорные ∩ первые k абзацев| / |опорные|, для k = 2 и 5. Метрика набора — среднее по вопросам.
- **Разности** — парный бутстреп по вопросам, 10 000 повторов, seed 0, 95 % интервал. Считаются:
  - (в) − (а): **главная**;
  - (б) − (а): вклад BM25 и RRF без графа;
  - (в) − (б): вклад графа сверх гибридного старта;
  - (г) − (а) и (г) − (в): вклад переранжирования.
  - Всё, кроме главной, описательно, без поправок.
- **По типам вопросов:** MuSiQue — 2hop / 3hop / 4hop; 2Wiki — по полю `type`. Описательно.
- **В отчёт `reports/result_bench1.md`:**
  - таблица Recall@2 и @5 по вариантам;
  - разности с интервалами;
  - наш прирост (в) − (а) рядом с приростом HippoRAG 2 над NV-Embed-v2 (+5,0 / +13,9);
  - время и размеры графов;
  - 3 примера, выбранных до просмотра результатов по правилу: первые три вопроса MuSiQue, где (в) нашёл опорный абзац, а (а) нет, и столько же наоборот.

| (г) переранжирование 40 × 1 000 (GPU) | ≈ 3–5 мин | ≈ 3–5 мин |
| **итого** | **≈ 1,2–1,5 ч** | **≈ 45–60 мин** |

Всё в одной сессии Kaggle, до 12 ч; запас большой.

**Порядок действий:**
1. `python scripts/bench1_kaggle_pack.py kaggle/bench1/data`, затем `kaggle datasets create -p kaggle/bench1/data --dir-mode zip`. Датасет приватный: код и данные WordNet, без ключей и диалогов.
2. `kaggle kernels push -p kaggle/bench1`. Ядро приватное, GPU, интернет — для HF и spaCy по закреплённым ревизиям.
3. Ядро последовательно запускает `--dataset musique`, затем `--dataset 2wiki`, с `--device cuda --reranker fp32`. Выход — `out/{набор}/recall.jsonl` и `summary.json`.
4. `kaggle kernels output` → локально пишется отчёт `reports/result_bench1.md`.
5. Если ядро упадёт, перезапуск продолжает с места: граф только дописывается. Падение и его причина фиксируются в отчёте.

## 8. Риски и известные ограничения

- **Энкодер слабее, чем у HippoRAG 2:** e5-base против NV-Embed-v2. Абсолютные числа ниже ожидаемы, поэтому критерий построен на приросте над собственным dense.
- **Параметры подобраны на русском отладочном наборе.** Порог синонимии 0,965 для английских абзацев может оказаться не тем. По правилу он не подбирается; если граф получится вырожденным (например, синонимов ≈ 0 или взрыв), это фиксируется как наблюдение.
- **Числовые сущности исключены из понятий.** Мосты-годы и мосты-числа в MuSiQue (на проверке 4 промаха из 30) граф не свяжет через понятие — только через тексты предложений.
- **Наши предложения ≠ их абзацы.** Перевод в абзацы через максимум честен для Recall по абзацам, но (а) у нас — dense по предложениям, а не по абзацам целиком, как у NV-Embed-v2 в статье.
- **Время записи в граф** оценено по малому корпусу. На полном корпусе запросы в SQLite могут замедлиться; сессии Kaggle хватит с запасом.

## Поправки

**Поправка 1 (2026-10-30, до получения каких-либо результатов — первый прогон упал на построении графа):**
- *Причина падения:* Kaggle распаковал `wordnet.zip` во вложенную папку (`corpora/wordnet/wordnet/`). На абзаце, который ушёл по пути извлечения без spaCy (редкий не-английский текст), NLTK не нашёл WordNet. До падения граф MuSiQue записал 7 766 из 11 656 абзацев за ~3 ч, ≈ 1,4 с на абзац.
- *Исправления, только технические:*
  - ядро распрямляет папки WordNet;
  - при массовой записи корпуса коммит идёт раз в 500 абзацев вместо каждого;
  - SQLite работает с `synchronous=NORMAL`;
  - spaCy заранее прогоняется по всем предложениям через `nlp.pipe` с кэшем.
- *Почему это не меняет анализ:* содержимое графа не меняется. Проверено: пакетный spaCy совпадает с поштучным; отладочный граф на 10 вопросах совпадает с прежним до последнего ребра (3 004 понятия, 9 226 рёбер, те же Recall). Варианты, параметры, метрика и критерий не менялись. Прогон начинается заново.
