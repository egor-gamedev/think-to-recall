## 1. Вопрос

Находит ли граф решающий факт, семантически далёкий от вопроса, лучше своей базы:
- (а) поверх обычной dense-памяти;
- (б) поверх поискового стека в стиле EverMemOS?

## 3. Варианты этапа 1 (все в одном прогоне)

| | вариант | что это |
|---|---|---|
| **A** | обычная память | dense e5-base по единицам; оценка единицы — максимум по предложениям |
| **B** | только граф | PPR только от понятий вопроса (вес IDF, damping 0,5), без dense; для справки |

| **D** | D0 + шлюз графа | база — выдача D0 |

**D0 — поисковый стек EverMemOS без LLM-построения памяти.** Собран из их же открытой библиотеки `everalgo` (Apache-2.0; everalgo-rank 0.3.0, everalgo-clustering 0.2.1 — версии, которые закрепляет EverOS @ 648b34b) и повторяет 1:1 их бенчмарк (EverAlgo @ 7398133, `benchmarks/common/stages/search.py`), настройки — из их `benchmarks/common/config.py`, **ничего не подбирается**:
- **единицы («эпизоды»)** — записи памяти IMLogic или сессии ImplexConv; «атомарные факты» — сама запись или предложения сессии. Построения памяти через LLM (MemCell, Foresight, профиль) **нет**;
- **dense** — MaxSim по эмбеддингам фактов (Qwen3-Embedding-4B @ 5cf2132, 1024 измерения); **sparse** — MaxSim по BM25 фактов (их токенизация NLTK + Porter); `hybrid_full` = RRF (по 50 кандидатов, k = 40);
- **MemScene** — `cluster_by_geometry` (косинус ≥ 0,70, окно 7 дней; у ImplexConv меток времени нет — окно не действует); выбираются 10 сцен, их участники переранжируются Qwen3-Reranker-4B @ 22e6836 с их инструкцией; первые 10;
- **итог** — первые 10 раунда 1, затем остальной `hybrid_full` (чтобы Recall@k был определён и после 10).

**D+ (D + проверка достаточности через LLM) — отложен на «потом»**, в этот прогон не входит: вызовов LLM на этапе 1 нет.

**Именование.** D0 называется «поисковый стек EverMemOS без LLM-построения памяти». Сравнение D и D0 формулируется как «граф поверх поиска в стиле EverMemOS», **не «лучше EverMemOS»**. Сравнение с настоящей EverMemOS возможно, только если авторы IMLogic пришлют построенную память — вопрос есть в письме (`reports/imlogic_letter_draft.md`, п. 5).

## 4. Метрика и заранее заданные сравнения

**Основная метрика** — Recall@5 по эталону: `memory_l` для IMLogic, сессии-доказательства для ImplexConv.

**Описательно:**
- Recall@1/10/30 (IMLogic) и @1/3/10 (ImplexConv);
- `memory_s` (IMLogic);
- opposed и supportive отдельно (ImplexConv);
- разбивка по категориям.

**Сравнения** — 2 на каждый набор, **4 теста, поправка Холма на все четыре:**

| | сравнение | что проверяет |
|---|---|---|
| S1 | **C против A** | граф поверх обычной памяти |
| S2 | **D против D0** | граф поверх поиска в стиле EverMemOS |
| — | B | только для справки, без теста |

- **Тест** — как в bench1b: односторонний парный перестановочный со сменой знака по вопросам, 10 000 перестановок, seed 0. Значимо — p по Холму < 0,05. Плюс 95 % бутстреп, победы и поражения.
- **Ничья** (незначимая разность) означает «без модуля»: модуль не включается.
- **Проверка реализации** — инвариант «нет изменения — выдача = база» проверяется для C и D на каждом вопросе. При нарушении прогон недействителен.

## 5. Критерий «продолжать или нет» (зафиксирован до прогона)

- Критерий относится к **графу от вопроса** (старты графа — только вопрос и выдача базы).
- **Продолжать:** C значимо лучше A хотя бы на одном наборе (S1 на IMLogic или на ImplexConv), **и** D не хуже D0.
  - «Не хуже» — на обоих наборах D не значимо хуже D0: обратный односторонний тест той же схемы (D0 > D), p > 0,05 без поправки. Это строже для нас, чем с поправкой.
- **Остановиться или менять подход:** граф (S1 и S2) **нигде** не даёт значимого прироста над своей базой.
- **Промежуточный случай** (прирост есть, но незначимый, или значимый только на одном наборе без «D не хуже D0»): в отчёте — «неоднозначно», без вывода «работает».
- **Отрицательный результат этапа 1 не закрывает гипотезу рукавов из шагов мышления — она проверяется на этапе 2** (`reports/prereg_stage2.md`).

## Поправка 1 (2026-11-07, техническая, до каких-либо результатов основной части)

- Первый запуск основной части IMLogic (ядро v6) упал на старте стадии graph, ещё до любых выдач.
  - Причина: в HaluMem есть битые метки времени вида «Aug 12, 2040, 2040, 13:33:11» (год повторён).
  - Исправление: разбор берёт месяц, день, первый год и время. Метки нужны только для окна сцен в D0.
- В той же версии кода у шлюза появился необязательный параметр `extra_anchors` для этапа 2. Без него поведение тождественно, это проверено тестами шлюза.
- Остальное без изменений.

## Поправка 2 (2026-11-08, техническая, до просмотра любых результатов ImplexConv)

- Основной прогон ImplexConv (ядро v8) упал на стадии эмбеддингов, примерно через час после старта. A, B и C к этому моменту были посчитаны, но **не просматривались**, а частичный выход удалён.
- Причина: у 5 opposed-примеров (`opposed52`, `opposed295`, `opposed483`, `opposed894`, `opposed1272`) после отбора вопросов не осталось ни одного вопроса, а склейка эмбеддингов пустого списка падает.
- Исправление: для таких примеров записывается пустой массив. На вопросы и метрики это не влияет: их по-прежнему 855.
- ImplexConv перезапускается целиком, новой версией ядра. Остальное без изменений.
- **Уточнение к поправке 2 (2026-11-08):** первое исправление было ошибочным: `reshape` пустого массива. Перезапуск v9 упал на той же стадии, тоже без просмотра результатов. Исправлено: для примера без вопросов пишется массив нужной формы (0 × размерность); проверено локально на примере с 0 вопросов. Перезапуск — v10. Кроме того, ядро теперь удаляет промежуточные файлы и при падении.

## Поправка 3 (2026-11-08, техническая, до просмотра любых результатов ImplexConv)

- Перезапуск ImplexConv v10 прошёл исправление поправки 2, но упал на стадии эмбеддингов, на 195-м примере из 200: не хватило памяти GPU на пакет с очень длинными предложениями. Результаты не просматривались, промежуточные файлы удалены ядром.
- Исправление: при нехватке памяти пакет кодируется заново половинами, вплоть до одного предложения. Модель, обрезка и параметры те же; проверено локально.
- Перезапуск — v11. Остальное без изменений.
- **Уточнение к поправке 3 (2026-11-08):** v11 упал там же, тоже без просмотра результатов.
  - Причина: в `supportive774` есть «предложение» на 13 260 символов (разбиение на нём не сработало). Повтор с меньшим пакетом выполнялся внутри обработчика исключения, а оно держит память прошлой попытки; поэтому свободной памяти с каждым повтором становилось меньше.
  - Исправлено: повтор выполняется после выхода из обработчика, с освобождением памяти. Логика проверена локально.
  - Заодно примеры без вопросов (поправка 2) пропускаются на всех стадиях — вопросы и метрики те же.
  - При падении ядро теперь сохраняет чекпоинты в выход, и ядро `ctxgraph-implicit-resume` продолжает с них.
  - Перезапуск — v12.
