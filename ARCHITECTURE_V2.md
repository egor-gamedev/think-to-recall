# ctxgraph — архитектура v2 (утверждена Егором 2026-10-30, с правками)

> Статус: **утверждена с правками Егора** (§3.2 английский путь, §3.8 бюджет задержки, §3.14
> интерфейс к модели, §6 оценка вычислений и Recall@5 по абзацам, §7 ответы). Реализация начинается
> с демо на crypto-wallet.
> Основа: `ARCHITECTURE_REVIEW.md` (задание и дополнения Егора), `reports/arch_00_current.md` (как
> устроено сейчас), проверка GLiNER на русском — `reports/arch_gliner_ru.md`.
> Язык: документ для Егора — по-русски. Идентификаторы (таблицы, типы узлов и рёбер, имена функций) —
> по-английски, как они будут в коде.

## 0. Принципы

1. **Заимствовать по максимуму.** У каждой части есть строка «откуда взято». Своё — только там, где
   готового нет: рукава мышления, периферия, закрепление и сокращения, и мелкие адаптации (русский
   язык, работа без генеративной модели при построении).
2. **Строит граф не генеративная модель.** Извлечение, связи, смена решения — малые кодировщики
   (GLiNER, эмбеддинги, cross-encoder) и правила. Ни одного вызова LLM на построение памяти. Это
   главное отличие от HippoRAG 2, LightRAG и Graphiti: у них извлечение делает LLM.
3. **Только дозапись.** Граф обновляется инкрементально и никогда не перестраивается целиком. Ничего
   не удаляется: смена решения помечает старую связь недействительной (с временем).
4. **Фрагменты текста — полноправные узлы.** Подход «только сущности» теряет контекст: в HippoRAG 2
   без узлов-фрагментов полнота поиска (Recall@5) падает с 87,1 до 81,0 в среднем по трём наборам
   (MuSiQue −11,0); у нас на этапе A рукава-сущности ничего не дали сверх поиска по вопросу.
5. **Межсессионный граф одного пользователя.** Multi-user features are out of scope of this repository.
6. **Внутри — английский.** Код, метки узлов и рёбер, брифы и отчёты подсессий. Вход — любой язык:
   эмбеддинги и переранжирование мультиязычные; понятия по возможности привязаны к Wikidata QID.
7. **Тесты — только маленькие (≤ 5 минут) и только для отладки.** Выводы — только на чужих бенчмарках,
   одним замороженным прогоном с пре-регистрацией. E1b / E1c / E3 — набор для отладки.

## 2. Модель данных (личный слой, один SQLite на пользователя)

```
episodes   (id, session_id, role, author, ts, source, text_redacted, redactions_json)
fragments  (id, episode_id, idx, text, lang, emb BLOB)           -- sentence nodes
concepts   (id, label_en, surface, lang, qid NULL, ili NULL, kind, emb BLOB, first_seen_ts)
mentions   (fragment_id, concept_id, span_start, span_end, extractor, score)   -- edge "contains"
edges      (id, src_concept, dst_concept, rel, weight,
            t_valid, t_invalid NULL, t_created, t_expired NULL,  -- bi-temporal, Graphiti-style
            episode_ids_json, extractor)                          -- rel: cooccur | synonym | replaces | typed
supersedes (new_fragment, old_fragment, t, detector, evidence)   -- decision changes (replaces)
fts_fragments USING fts5(text)                                    -- BM25, incremental
usage      (edge_id, session_id, ts, kind)                        -- consolidation interface (part 10)
```

- **Узлы графа для PPR:** `concepts` ∪ `fragments`. Рёбра: `contains` (из `mentions`, вес 1),
  `cooccur`, `synonym`, `replaces` (из `edges`), и «фрагмент → следующий фрагмент того же эпизода»
  (контекст, слабый вес).
- **Время.** `t_valid` — когда связь стала верной (время эпизода), `t_invalid` — когда перестала
  (время эпизода со сменой решения). `t_created` / `t_expired` — время записи в базу (как в Graphiti:
  отделяем «когда было в разговоре» от «когда записали»).
- **Провенанс.** Любой фрагмент → эпизод; любое понятие → упоминания → фрагменты → эпизоды; любое
  ребро → список эпизодов.

## 3. Части подробно

### 3.1 Приём (эпизоды) — **из Graphiti**

- **Берём:** понятие эпизода: сырой ввод хранится как эпизод с временем; всё извлечённое ссылается на
  эпизод (Graphiti, Apache-2.0; Zep, arXiv 2501.13956).
- **У нас:** эпизод = одна реплика (пользователь / ассистент / результат инструмента) с `session_id`.
  Текст проходит фильтр приватности **до** записи (ч. 3.11); хранится только очищенный текст.
- **Отличие:** Graphiti извлекает сущности и связи LLM-ом; у нас — ч. 3.2.
- **Риск:** длинные реплики с кодом. Код не режется на предложения: блок кода — один фрагмент-«код»
  без эмбеддинга по тексту, только идентификаторы (как сейчас в `ingest.py`).

### 3.2 Извлечение без генеративной модели — **GLiNER + наш извлекатель**

- **Берём:** GLiNER `urchade/gliner_multi-v2.1` (Apache-2.0, ~209 М параметров, библиотека
  `gliner` 0.2.29) — именованные сущности с метками (person, organization, location, software,
  product, hardware, date, quantity).
- **Проверка на русском (30 реплик, `reports/arch_gliner_ru.md`):**
  - имена собственные GLiNER ловит хорошо и целиком («Олег Викторович» — одна персона; Steam,
    GodotSteam, GDExtension — software);
  - но понятий (не имён) находит мало: 5,1 сущности на реплику против 13,4 у нашего извлекателя;
    доля лемм текста факта среди извлечённого — 24 % против 52 %;
  - метки иногда неверны («хирургам» — organization, Windows — hardware);
  - 0,49 с на реплику на CPU.
- **Решение (утверждено):** гибрид. GLiNER — для имён и их типов (и как кандидаты на привязку к
  Wikidata); наш извлекатель (`ingest.extract_entities`: ключевые фразы YAKE, леммы-существительные
  pymorphy3, идентификаторы, регулярки) — для понятий. Объединение по пересечению спанов.
- **Английский путь (правка Егора):** для английского текста леммы и именные группы — spaCy
  (`en_core_web_sm`, MIT: лемматизатор, `noun_chunks`, NER), вместо pymorphy3 и наших правил для
  русского. Язык определяется по фрагменту. **До запуска чужих бенчмарков** — проверка на 30
  английских абзацах (например, из MuSiQue): тот же отчёт, что `reports/arch_gliner_ru.md`
  (сущностей на абзац, покрытие лемм ответа/опорного факта, время). На больших английских корпусах
  GLiNER на CPU слишком медленный (≈ 0,5 с на реплику) → по умолчанию имена из NER spaCy, GLiNER —
  на GPU или выключен.
- **Связи:** по решению Егора типы не обязательны → связь `cooccur` между понятиями одного
  предложения (вес — по числу предложений и сессий, PMI как в нынешнем «опыте»). GLiREL
  (`jackboyla/glirel-large-v0`) — для типизированных связей: **проверить** (лицензию и русский) на тех
  же 30 репликах; без проверки не включаем.
- **Отличие от HippoRAG 2:** там OpenIE-тройки делает Llama-3.3-70B (≈ 1 вызов LLM на фрагмент); у нас
  0 вызовов. Цена — связи без типов и более шумные понятия; компенсируем узлами-фрагментами и
  cross-encoder на отборе.
- **Риски:** шум понятий («куча», «старт»); синонимия RU/EN («база» / «database») — закрывается
  рёбрами `synonym` (ч. 3.3) и привязкой к QID (ч. 3.13).

### 3.3 Структура — **из HippoRAG 2**

- **Берём:** узлы-понятия (phrase nodes) и узлы-фрагменты (passage nodes); рёбра `contains`
  (фрагмент → его понятия), `synonym` (понятия с близостью эмбеддингов выше порога; в HippoRAG 2 —
  0,8 для NV-Embed-v2), связи между понятиями (там — тройки OpenIE) (HippoRAG 2, ICML 2025,
  arXiv 2502.14802; код MIT).
- **У нас:**
  - фрагмент = **предложение** (единица отбора в память, ч. 3.8); эпизод-реплика — родитель, рёбра
    «соседнее предложение» дают контекст;
  - связи понятие–понятие — `cooccur` (+ `typed`, если GLiREL пройдёт проверку);
  - порог `synonym` для multilingual-e5 подбирается заново (у e5 косинусы выше в среднем, 0,8 не
    переносится): по 50 размеченным парам из отладочного набора.
- **Риск:** взрыв числа рёбер `cooccur` в длинных предложениях → ограничение: только понятия с
  df ниже порога «частых» (как `Archive.common` сейчас), не больше N пар на предложение.

### 3.4 Обновление — **LightRAG + Graphiti**

- **Берём:**
  - LightRAG (arXiv 2410.05779, MIT): новый документ обрабатывается отдельно, его маленький граф
    сливается с основным объединением множеств узлов и рёбер, без перестройки индекса;
  - Graphiti: у ребра интервал верности; при противоречии старое ребро получает `t_invalid`, а не
    удаляется.
- **У нас при новой реплике** (только дозапись):
  1. `episodes` += реплика; `fragments` += её предложения (+ эмбеддинги, + FTS5);
  2. понятия: существующее (по канонической форме / QID / `synonym` выше порога) — дописываем
     упоминание; новое — новая строка;
  3. рёбра `cooccur`: существующее — увеличиваем вес и дописываем эпизод; новое — вставляем;
  4. **смена решения:** детектор «заменяет» (`ctxgraph/e1b/replaces.py`, точность 9/10 по разметке
     Егора) находит старый фрагмент → строка в `supersedes`; рёбра, которые держались только на
     старом фрагменте и противоречат новому (то же понятие-«слот», другое значение), получают
     `t_invalid = время новой реплики`. Ничего не удаляется.
- **Отличие:** LightRAG при слиянии резюмирует описания LLM-ом, Graphiti решает о противоречии
  LLM-ом; у нас — правила и малые модели.
- **Риски:**
  - полнота детектора смены ≈ 28 % (8/29): большинство неявных смен не ловится → старое не гаснет;
    это главный известный риск части; варианты усиления — cross-encoder NLI на парах «новое
    предложение — старые предложения про то же понятие» (без генеративной модели) — **проверить**;
  - слияние понятий по `synonym` может склеить разные вещи → слияние только как ребро, не как
    объединение узлов.

### 3.5 Хранение

- SQLite в режиме WAL (стандартная библиотека Python), FTS5 для BM25 (встроен в SQLite), эмбеддинги —
  BLOB + индекс в памяти, дополняемый при записи (на десятки тысяч предложений достаточно; при росте —
  `sqlite-vec`, проверить лицензию).
- Один файл на пользователя.
- **Сейчас** бенчмарк-память пересобирается на каждый вопрос (`arch_00_current.md`) — в v2 этого нет.

### 3.6 Поиск стартовых узлов — **оставляем гибрид**

- dense (multilingual-e5-base, MIT) + BM25 (FTS5) по фрагментам → RRF; понятия запроса — точное
  совпадение / лемма / QID → стартовые узлы-понятия.
- Эмбеддинги считаются по предложению, а не по первым 200 токенам реплики (сейчас факт в конце
  длинной реплики невидим для dense-поиска).

### 3.7 Распространение — **PPR из HippoRAG 2**

- **Берём:** персонализированный PageRank от стартовых узлов; в HippoRAG 2 — затухание (damping) 0,5,
  стартовые веса фрагментов × 0,05 относительно понятий.
- **У нас:** без LLM-фильтра троек («recognition memory» HippoRAG 2): его роль — у cross-encoder на
  отборе. PPR — разреженное степенное умножение на scipy (BSD) по подграфу вокруг стартов (без
  igraph: GPL). Недействительные рёбра (`t_invalid` не пуст) в PPR не участвуют, но их фрагменты
  доступны с пометкой «позже заменено».
- **Отличие:** заменяет нынешнее «1 шаг по графу + бонус пересечений».
- **Риск:** параметры HippoRAG 2 подобраны на английских вики-корпусах; перенос на диалоги — проверять
  на чужих бенчмарках (LongMemEval), не на наших.

### 3.8 Отбор в память — **cross-encoder**

- `BAAI/bge-reranker-v2-m3` (Apache-2.0, ревизия 953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e),
  единица — предложение, соседнее предложение — как контекст, если влезает; бюджет — параметр
  (сейчас 600 токенов). Код есть: `ctxgraph/e1b/selection.py` (перенесём).
- **Бюджет задержки (правка Егора): поиск в продукте — до 1–2 с на CPU.** Замер: bge-reranker-v2-m3
  на нашем CPU ≈ 5–6 пар/с, e5-base ≈ 20 предложений/с — в 1–2 с не укладывается. Поэтому два
  режима:
  - **продукт (CPU):** эмбеддинги предложений считаются при записи (не при поиске); при поиске —
    1 эмбеддинг запроса + FTS5 + PPR (миллисекунды); на переранжирование — **не больше 20–30
    предложений** после PPR, лёгким мультиязычным cross-encoder; если не укладывается — без
    переранжирования (порядок PPR + близость эмбеддингов);
  - **бенчмарки (GPU Kaggle):** bge-reranker-v2-m3, кандидатов больше (top-60).
- **Лёгкие мультиязычные cross-encoder (лицензии):**

  | модель | размер | лицензия | годится |
  |---|---|---|---|
  | `BAAI/bge-reranker-v2-m3` | 568 М | Apache-2.0 | бенчмарки на GPU |
  | `Alibaba-NLP/gte-multilingual-reranker-base` | 306 М | Apache-2.0 | кандидат для продукта |
  | `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` | ≈ 118 М | Apache-2.0 по перезаливке, **сверить карточку оригинала** | кандидат для продукта (самый лёгкий) |
  | `jinaai/jina-reranker-v2-base-multilingual` | 278 М | **CC-BY-NC-4.0 — некоммерческая, не берём** | нет |

  Выбор — замером задержки и качества на отладочном наборе (≤ 5 мин), до бенчмарков.

### 3.9 Рукава мышления — **своё**

Что взято: IRCoT (поиск после каждого шага рассуждения); FLARE — поиск в момент неуверенности
(для сравнения); PPR — из ч. 3.7.

1. Модель думает шагами (≤ 3), затем отвечает.
2. **Рукав = группа слов шага** (2–6 слов, одна тема): именная группа вокруг понятия
   (`v9.phrase_sleeves`: морфология pymorphy3 для русского; для английского — noun chunks spaCy,
   проверить); до 4 рукавов на шаг.
3. **Мини-граф рукава** = PPR от стартовых узлов этого рукава (фрагменты и понятия, найденные по
   тексту рукава, ч. 3.6) → узлы с весами (понятия + фрагменты).
4. **Пересечение рукавов** = узлы с весом выше порога в ≥ 2 мини-графах (этого шага или прошлых).
5. **Периферия:** ≤ 20 % контекста шага; порядок — пересечения, затем прочее; вес по глубине 0,5^d,
   максимум d = 3; якорь цели — близость к исходному вопросу; блок помечен «необязательно, не
   требования». Повторно показанное не подаётся.
6. В память при ответе — отбор ч. 3.8 по объединению фрагментов мини-графов.

- **Что уже известно:** рукава из **вопроса** (не из шагов) при равном размере пула ничего не дают
  сверх поиска по всему вопросу (E1d, этап A3). Остаётся гипотеза про рукава **из шагов мышления**.
- **Контроль** при проверке: те же шаги, один поиск (PPR) по всему тексту шага (IRCoT-подобно).
- **Риски:** пустые шаги у некоторых моделей (Mistral Large 4 в пробе: 8 из 15 шагов пустые —
  протокол чинить); рост стоимости в 4 раза (3 шага + ответ).

### 3.10 Закрепление и сокращения — **своё, только интерфейс**

- `record_usage(edge_id | fragment_id, session_id, kind)` — что из памяти попало в ответ (пользa, не
  выбор); `reinforce(...)` — бонус к весу с медленным затуханием (полураспад, как сейчас в

### 3.14 Интерфейс к модели (правка Егора)

Два режима: **продукт** (мы не управляем шагами модели) и **бенчмарки** (управляем).

**Как граф получает реплики (продукт):**
- **MCP-сервер** с инструментами по образцу Graphiti MCP (`add_memory` — эпизод с временем,
  `search_memory_facts`, `search_nodes`, `get_episodes`, `delete_episode`) и OpenMemory / Mem0
  (`add_memories`, `search_memory`, `list_memories`, `delete_all_memories`). У нас:
  - `remember(text, role, session_id, ts)` — записать эпизод (дозапись, ч. 3.4);
  - `recall(text, budget)` — поиск: стартовые узлы → PPR → отбор; ответ — блок памяти с id
    фрагментов и пометкой «воспоминания, не требования»;
  - `recall_sleeves(step_text)` — рукава мышления (ч. 3.9) по тексту шага;
  - `get_episodes(session_id, limit)`, `forget_episode(id)` — забыть эпизод по просьбе
    пользователя: эпизод и его фрагменты помечаются удалёнными (`t_expired`), из поиска уходят;
    физически не стираются, кроме явного запроса «стереть» (это одно место, где допустим `DELETE`, —
    право пользователя на удаление);
  - `mark_useful(fragment_id)` — интерфейс закрепления (ч. 3.10).
  Описания инструментов — данные, не инструкции (как сейчас в `mcp_server.py`).
- **Хуки Claude Code** — запись без участия модели: `Stop` (после ответа) и `PreCompact` (перед
  сжатием) читают `transcript_path` и дописывают новые реплики в граф; `UserPromptSubmit` может
  подкладывать результат `recall(prompt)` в контекст до ответа. Хук не зависит от того, вызовет ли
  модель инструмент. Для других клиентов — тот же путь через MCP `remember`.

**Откуда рукава в реальном использовании** (шагов модели не видно):
1. **Инструмент `recall_sleeves(step_text)`** — модель вызывает после шага рассуждения по инструкции
   в описании инструмента («после каждого шага, где упоминаешь факты проекта, передай текст шага»).
   Работает только с моделями, которые надёжно зовут инструменты; число вызовов не контролируем.
2. **Рукава из видимого текста ответа / промежуточных сообщений** — хук `Stop` строит рукава по тексту
   ответа и подкладывает периферию к **следующему** ходу (отставание на один ход, зато без участия
   модели).
3. **Рукава из запроса пользователя** — уже проверено (E1d, этап A3): при равном пуле ничего не дают
   сверх поиска по запросу; оставляем только как запасной режим.
По умолчанию: 2 + `recall(prompt)` через хук; 1 — для моделей с надёжным вызовом инструментов.

**Решение Егора (2026-10-30): в продукте планирует сама модель.** Она рассуждает шагами и после
каждого шага вызывает `recall(step_text)` (инструкция в описании инструмента); рукава строятся из
`step_text` автоматически. Варианты 2–3 выше остаются запасными для моделей, которые не зовут
инструменты.

**Планировщик шагов для отладки и бенчмарков** (`ctxgraph/v2/planner.py`). Заимствуем:
- из **IRCoT** (Trivedi и др., 2023) — порядок «сначала поиск по вопросу, затем рассуждение, затем поиск
  по тексту рассуждения»; в отличие от IRCoT шаги пишутся одним вызовом (дешевле), а не по одному с
  поиском между ними;
- из **Self-Ask** (Press и др., 2023) — разбиение вопроса на подвопросы / шаги, по которым ищут
  отдельно; у нас каждый шаг — источник рукавов (групп слов), а не одного поискового запроса.
Протокол: та же модель, что отвечает, видит вопрос и первый блок памяти (поиск по вопросу) и пишет до
3 коротких шагов без ответа → рукава из шагов → мини-графы → итоговый блок (гибрид, ч. 3.8) → ответ.

**Протокол для бенчмарков** (отдельно, как сейчас — `ctxgraph/e1b/steps.py`): мы сами задаём шаги
(≤ 3 шага + ответ), после каждого шага — поиск по рукавам шага; контроль — поиск по всему шагу.
Числа из бенчмарков с этим протоколом **не переносятся** на продукт без проверки режима 1 / 2.

### 3.15 Импорт существующей переписки (правка Егора; описание, реализация — после 3.14)

Задача: человек подключает MCP к чату, где уже есть история, — история становится графом.

- **Импорт = проигрывание реплик по порядку** с исходными временами через тот же путь дозаписи
  (`Graph.add_episode`, ч. 3.4), включая смену решения и недействительность рёбер. Инвариант «по
  одной == пачкой» уже проверяется тестом.
- **Откуда взято:** массовая загрузка эпизодов в Graphiti (`add_episode_bulk` со списком `RawEpisode`:
  имя, содержимое, источник, описание источника, `reference_time`). Берём формат пачки и исходные
  времена. **Не берём** упрощение Graphiti: их массовый путь пропускает недействительность рёбер
  (по их документации — только для пустых графов); у нас недействительность дешёвая (правила), поэтому
  импорт идёт полным путём.
- **Источники:**
  - файл переписки Claude Code из хуков (`transcript_path`) — автоматически при первом подключении,
    **только с согласия пользователя**;
  - выгрузки ChatGPT (`conversations.json`) и claude.ai (экспорт данных);
  - простой текст (реплики по строкам / блокам с ролями).
- **Чат уже сжимался:** эпизоды из резюме записываются с `source=summary` и пониженным доверием
  (вес фрагмента при отборе × коэффициент, как у реплик модели; пометка «из резюме» в памяти).
- **Идемпотентность:** эпизод узнаётся по хэшу (сессия, роль, очищенный текст, исходное время);
  повторный импорт ничего не дублирует (`INSERT OR IGNORE`, как сейчас).
- **Приватность:** фильтр — до записи, как для обычных реплик (ч. 3.11).
- **Демо:** кнопка «импортировать переписку» и отчёт: сколько эпизодов, сколько из резюме, что
  отфильтровано (тип и место, без значений).

### 3.16 Вес связи зависит от контекста (требование Егора, 2026-11-08; описание, реализация — после этапа 2)

**Проблема.** Сейчас вес `cooccur` — общая встречаемость: `log1p(число предложений)` в PPR (`graph.py::_adj`). Редкость в шлюзе — тоже глобальная (IDF по всему корпусу).
- Понятие, которое часто встречается с разными темами («работа», «проект», «Python»), получает много тяжёлых рёбер и становится **хабом**. Масса PPR утекает через него в чужие темы.
- Пересечение рукавов (ч. 3.9, п. 4) и шлюз (≥ 2 стартов) срабатывают на хабах: хаб «пересекается» со всем.
- Отсюда требование: **узел не должен быть хабом внутри конкретного контекста.** Вес связи считается в контексте, а не по всему корпусу.

**Что такое контекст.** Иерархия от узкого к широкому:
1. **Понятия рукава** — набор редких понятий рукава или шага плана (то, по чему рукав искал).
2. **Кластер контекста** — группа эпизодов одной темы:
   - кластеры по эмбеддингам и времени, как MemScene (`cluster_by_geometry`, ч. 6);
   - или по общим редким понятиям.
3. **Сессия / проект.**
4. **Весь граф** пользователя.

**Варианты веса (сравнить на dev, выбрать один):**
- **(а) Условный PMI внутри кластера.** Для пары понятий a, b в контексте c:
  `w(a,b | c) = max(0, log( n(a,b|c) · N(c) / (n(a|c) · n(b|c)) ))` (PPMI), где n — число предложений контекста c с понятием или парой, N(c) — всего предложений в c.
  - Хаб, встречающийся во всех предложениях кластера, получает PMI ≈ 0 со всеми — внутри этого кластера он не проводит массу.
  - Сглаживание: прибавка α к счётчикам (α = 0,5 по умолчанию).
  - Переход PPR для запроса — смесь матриц контекстов с весами P(c | запрос или рукав).
- **(б) Гиперграф с узлами-контекстами.**
  - Понятие связано не с понятием, а с узлом-контекстом; вес — специфичность понятия для контекста: `log(n(a|c)·N / (n(a)·N(c)))`, как TF-IDF.
  - Путь «понятие → контекст → понятие» проходит только через контексты, где оба понятия специфичны. Хаб получает малый вес во всех контекстах сразу.
  - Легче обновлять (одно ребро на пару «понятие–контекст», не O(понятий²)), и он естественно ложится на PPR HippoRAG (узлы-фрагменты уже есть; контекст — ещё один тип узла).

**Откат при нехватке данных.**
- Если пара встречена в контексте c меньше `m` раз (m = 3) или в c меньше `N_min` предложений, вес берётся из более широкого контекста по иерархии выше (рукав → кластер → сессия → пользователь).
- Не жёсткое переключение, а интерполяция, как в языковых моделях с откатом (Witten–Bell):
  `w_c = λ_c · PMI_c + (1 − λ_c) · w_parent(c)`, где `λ_c = n_c / (n_c + β)`.
  - Мало данных в контексте — вес ближе к широкому, много — к своему.
- В отчёте — доля пар, ушедших в откат, по уровням.

**Проверка (после этапа 2, только dev):**
- **Метрика хабов:** доля массы PPR на 1 % узлов с наибольшей степенью; число кандидатов шлюза на вопрос. Цель — меньше хабов при том же Recall.
- **Поиск:** R@5 на dev MuSiQue / IMLogic / ImplexConv — новый вес против нынешнего `cooccur`, шлюз прежний.
- **Тесты:**
  - синтетический хаб (одно понятие во всех предложениях двух тем) не проводит массу PPR между темами;
  - откат при n < m даёт вес широкого контекста;
- Выбор между (а) и (б) — по dev, до любой пре-регистрации на основной части.

- **Порядок (утверждён):** сначала метрики без судьи — Recall@5 на MuSiQue / 2Wiki и полнота поиска на
  LongMemEval по сессиям-доказательствам. Судью пока не выбираем.
- **Recall@5 — по абзацам, как в HippoRAG 2 (правка Егора).** У нас единица — предложение, у HippoRAG 2 —
  абзац (passage). Для честного сравнения оценка абзаца = максимум оценок его предложений (PPR /
  переранжирование), ранжируем абзацы, считаем долю опорных абзацев в top-5. Отдельно (не для
  сравнения) — Recall по предложениям.
- **Оговорка о сравнимости:** официальный судья LongMemEval — GPT-4o; бесплатный судья даст
  несравнимые абсолютные цифры. Сравнимы без судьи: полнота поиска, F1 на MuSiQue / 2Wiki.

**Оценка вычислений (правка Егора).** Замер на нашем CPU: e5-base ≈ 20 предложений/с, bge-reranker-v2-m3
≈ 5–6 пар/с, GLiNER ≈ 0,5 с на реплику. GPU Kaggle (T4 / P100) — оценка по типичной производительности,
**уточнить первым же запуском**: e5-base ≈ 500–1 000 предложений/с, bge-reranker-v2-m3 (fp16) ≈ 200–400
пар/с. Предложений в абзаце — ≈ 5 (оценка; уточнить при загрузке).

| набор | объём построения | граф на CPU | граф на GPU Kaggle | поиск 1 000 вопросов (60 пар на вопрос) |
|---|---|---|---|---|
| MuSiQue (11 656 абзацев) | 43 693 предложения (посчитано) | ≈ 1 ч (spaCy ≈ 135 предл./с + e5 ≈ 13–20 предл./с) | ≈ 6–7 мин | CPU ≈ 3 ч с переранжированием / минуты без; GPU ≈ 3–5 мин |

- **Пересчёт 2026-10-30 (`reports/v2_english_and_estimates.md`):** кэш по сессиям даёт только ×1,2 (сессии почти не повторяются между вопросами). Полный LongMemEval-S — ≈ 6–8 ч на Kaggle даже с GPU; варианты: подвыборка вопросов (100 вопросов ≈ 1,3–1,6 ч), spaCy в несколько процессов, сначала метрика поиска без LLM. Решение — Егору.
- **Кэш по сессиям для LongMemEval:** истории вопросов собраны из общего пула сессий; подграф сессии
  (эпизоды, предложения, эмбеддинги, понятия) строится один раз по id сессии и переиспользуется;
  граф вопроса = слияние подграфов его сессий (дозапись, ч. 3.4). Число уникальных сессий —
  посчитать при загрузке набора; выигрыш ожидается в разы.
- **Подвыборка для отладки (≤ 5 мин):** 50 вопросов MuSiQue / 2Wiki с их абзацами, 20 вопросов
  LongMemEval-S. Не для выводов.
- **Полный прогон:** на GPU Kaggle, одна замороженная конфигурация.
- **Оговорка о языке:** все чужие бенчмарки на английском; русский остаётся на отладочном наборе.

## 7. Решения Егора (2026-10-30)

1. GLiNER — для имён; понятия — наш извлекатель (для английского — spaCy, §3.2).
2. Multi-user features are out of scope of this repository.
3. Привязка к Wikidata по умолчанию офлайн; онлайн — только с разрешения пользователя.
4. Первыми — MuSiQue / 2Wiki Recall@5 (по абзацам) и полнота поиска LongMemEval.
5. Судью пока не выбираем: сначала метрики без судьи.
6. Реализация начинается с **демо на одном проекте (crypto-wallet)** — граф раньше бенчмарков.
