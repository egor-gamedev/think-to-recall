# E1b — бенчмарк «долгий проект»: понимание из накопленного контекста

> Для Claude Code, проект `ctxgraph/`. Заменяет E1 как основную проверку.
> Причины: в E1 был потолок (обычный ответ покрывал 97% требований), модель почти не
> вызывала `expand` (3 из 300), меню удвоило выдуманные требования, судьи
> расходились (κ = 0.52).

## 1. Идея бенчмарка (автор — Егор)

Один длинный чат на одну тему — **проект пользователя** (например, криптокошелёк).
Контекст **забивается до лимита и сжимается 3–5 раз**, как в реальной долгой работе.
После этого пользователь задаёт **далёкие, но связанные** вопросы. Хороший ответ
требует **понимания проекта из накопленного**, а не общего ответа.

Пример: из разговора известно, что пишется мобильное приложение. Пользователь
спрашивает про JWT. Плохой ответ — шаблонно «как встроить JWT в мобильное
приложение». Хороший — связать с проектом: «JWT нужен для сайта или для API вашего
бэкенда? Если планируется веб-версия — тогда…», и **удержать** новое знание («будет
ещё сайт» или «есть отдельный API») для следующих вопросов.

Важно: правильное поведение часто — **уточнить**, а не угадать (JWT бывает и в
мобильных приложениях — через API). Оценка должна это засчитывать.

## 2. Состав

- **Проекты:** не меньше 3 разных (например: криптокошелёк — мобильное приложение;
  интернет-магазин на Django; научная работа по биоинформатике). Один проект — один
  чат. Иначе результат будет про одну историю.
- **Загрузочная часть:** реалистичный диалог разработки, 3–5 заполнений контекста.
  Генерирует **не тестируемая** модель (сильная, через API), Егор просматривает
  выборочно. В диалоге намеренно рассыпаны **факты проекта** (платформа, стек,
  ограничения, решения, отказы от решений, изменения решений), каждый — с id.
- **Пробные вопросы:** не меньше 15 на проект, всего ≥ 45. У каждого заранее:
  - **опорные факты** — какие факты проекта (id) должны повлиять на ответ;
  - **ожидаемый вывод** — что хороший ответ понимает или уточняет;
  - **неуместные советы** — что плохой ответ предложит (шаблон без учёта проекта);
  - тип: «нужно вспомнить», «нужно связать два далёких факта», «нужно заметить, что
    решение менялось», «нужно уточнить».
- Часть фактов **меняется по ходу** (сначала Postgres, потом перешли на SQLite) —
  проверка, что модель держит актуальное, а не первое.

## 3. Модель

- **Маленькая**, чтобы дёшево и чтобы контекст забивался быстро: Qwen2.5-7B-Instruct
  или 3B (или аналог) на Kaggle (T4×2, 4-бит). Лимит контекста искусственно
  ограничить, например **8k токенов**, чтобы сжатий было 3–5.
- Маленькие модели плохо вызывают инструменты, поэтому основной механизм —
  **автоматическое раскрытие** (`auto_depth` 1–2), а не `expand` по выбору. Выбор
  модели остаётся в варианте 4.
- **Сжатие** одинаковое во всех вариантах: один и тот же способ резюме (одна модель,
  один промпт), чтобы различие было только в памяти.

## 4. Варианты

1. обычный чат + стандартное сжатие (резюме);
2. сжатие + поиск похожего по эмбеддингам (обычный RAG по истории);
3. сжатие + ctxgraph, `auto_depth = 1`;
4. сжатие + ctxgraph, меню, раскрытие по выбору модели;
5. контроль: сжатие + меню из случайных узлов того же размера;
6. **гибрид RAG + граф:** узлы — фрагменты собственной истории (реплики
   пользователя, ответы модели, решения) и сущности; вход — гибридный поиск
   (BM25 + эмбеддинги, top-k фрагментов); затем 1 шаг по графу (та же сущность,
   цепочка решений, рёбра «заменяет»); в промпт — **содержимое** 3–5 лучших
   фрагментов + меню ярлыков для остальных. Ответы модели хранятся с пометкой
   «сказано моделью» и ниже по доверию, чем слова пользователя.

Подсказки ctxgraph подаются **помеченными**: «это воспоминания и ассоциации из
прошлого разговора, не требования; используй, только если относится к вопросу» —
против выдумывания.

## 5. Оценка

Для каждого ответа, по заранее заданному списку (а не свободным суждением судьи —
так меньше расхождений):
- **опора:** сколько опорных фактов ответ учёл (0..N);
- **вывод:** понял или уточнил ожидаемое (да / нет);
- **неуместный совет:** дал ли шаблон, противоречащий проекту (да / нет) — главная
  метрика «не втюхивает»;
- **выдумка:** утверждает ли факт о проекте, которого не было (да / нет);
- **удержание:** в последующих вопросах использует ли вывод, сделанный ранее
  (отдельные пары вопросов).

Судья — сильная модель, не тестируемая, с рубрикой по спискам. Два судьи на 20%
ответов + ручная проверка Егором расхождений; κ в отчёт.

## 6. Пре-регистрация и критерии

До запуска: проекты, число вопросов, модель и версия, лимит контекста, способ
сжатия, варианты, метрики, тест (McNemar по вопросам для «вывод» и «неуместный
совет»; бутстреп по вопросам для «опоры»), поправка Холма.

**Успех идеи:** вариант 3, 4 или 6 лучше вариантов 1, 2 и 5 по «вывод» **и** не хуже по
«выдумке». Если ctxgraph лучше только варианта 1, но не 2 — граф не даёт больше
обычного RAG; так и писать.

## 7. Порядок

1. Сгенерировать один проект (загрузка + 15 вопросов), показать Егору.
2. Проба: 1 проект × 5 вариантов × 5 вопросов, проверить, что сжатия происходят и
   оценка работает.
3. Полный прогон после «да». Оценка стоимости — до запуска.
