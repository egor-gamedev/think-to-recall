# Задание V9 «рукава мышления» — для Claude Code, проект `ctxgraph/`

> Основа: `CONTEXT_GRAPH.md` (раздел «Рукава мышления»), итог E1c (`reports/result_e1c.md`),
> базовая линия `reports/e1c/main_final/v9_baseline.md`.
> Правила проекта прежние: пре-регистрация до любого запуска с API, спрашивать перед >300
> вызовами, ключи только в `.env`, «разведка» помечается, отчёты Егору — на русском.

## 0. Зачем

E1c показал: на «связать» ломается **извлечение**, а не модель. В памяти V6 — 23 % нужных
фактов и ни разу все сразу; то, что попало, модель использует в 84 %. Поиск одним запросом
по всему вопросу находит одну-две темы и теряет третью.

Гипотеза Егора: если мышление модели делить на **рукава** (темы шага), искать по каждому
отдельно и поднимать **пересечения** (узлы, достижимые из ≥ 2 рукавов), память принесёт
больше нужных фактов. Подсказки — периферия с малым весом, не уводящая от цели.

## 1. Варианты — сетка 2×2 (плюс база)

Одинаковые для всех: сжатие, окно, проекты, вопросы, модель-отвечающий, **суммарный бюджет
памяти на вопрос в токенах** (записать число; для многошаговых — сумма по шагам).

| | поиск по одному тексту | поиск по рукавам + пересечения |
|---|---|---|
| **один раунд, по вопросу** | V6 (есть) | **V9-q** |
| **по шагам мышления** | **V9-control** (IRCoT-подобный) | **V9** |

- **V9-q:** рукава из текста вопроса; по каждому рукаву — гибридный поиск (dense + BM25 +
  RRF) и шаг по графу; пересечения с бонусом; фильтр по якорю цели; один блок памяти.
  Генерации шагов нет → **полнота извлечения считается без API**.
- **V9-control:** модель думает короткими шагами (≤ 3 шага, затем ответ). После каждого шага
  — один гибридный поиск по **всему тексту шага**, как в V6. Без рукавов и пересечений.
- **V9:** те же шаги, но после каждого шага: рукава из текста шага → поиск и шаг по графу на
  рукав → пересечения → фильтр по якорю → периферия.

Протокол шагов одинаков для V9-control и V9 (тот же промпт, тот же лимит шагов).

## 2. Механизм V9 (детали)

1. **Рукава из текста:** сущности и ключевые фразы (уже есть `question_anchors` — обобщить на
   любой текст), до 4, редкие первыми. Число рукавов и правило выбора — записать.
2. **На каждый рукав:** гибридный поиск top-k по собственной истории + 1 шаг по графу (та же
   сущность, цепочка решений, «заменяет»), как в `v6_candidates`, но запрос = рукав.
3. **Пересечения:** узел, найденный от ≥ 2 разных рукавов (в этом шаге или с учётом рукавов
   прошлых шагов), получает бонус к баллу и идёт первым. Бонус — параметр, записать.
4. **Якорь цели:** кандидат отбрасывается, если его близость к исходному вопросу ниже порога
   (порог подобрать на 20 вопросах **проб**, не основных, записать до прогона).
5. **Периферия:** ≤ 20 % контекста шага; блок помечен «воспоминания и слабые ассоциации, не
   требования; используй, если относится к вопросу». Порядок: пересечения → прочее.
   Вес по глубине 0.5^d, максимум d = 3: на практике — доля бюджета и порядок.
6. **Не дублировать:** реплика, уже показанная на прошлом шаге, второй раз не подаётся.
7. **«Актуально» не включать:** разведка показала 70 % ложных «последних решений».
8. **Сокращения и закрепление в этом эксперименте выключены** (вопросы независимы, обучение
   между вопросами смешало бы результат). Это для E2.

## 3. Метрики

**Главная (без судьи):** полнота извлечения на «связать» — доля опорных фактов, попавших в
память полным фрагментом (`coverage.py`, объединение по шагам).
- **Главное сравнение:** V9 против V9-control, 60 вопросов «связать», парный бутстреп по
  вопросам, 95 % интервал. **Успех:** интервал разности выше 0 **и** разность ≥ +10 п.п.
- Вторичные (без поправок, описательно): V9-q против V6 (вклад рукавов без шагов);
  V9-control против V6 (вклад шагов без рукавов); то же на остальных типах; «все факты
  в памяти» (число вопросов).

**Вторичные с судьёй:** «вывод», «неуместный совет», «выдумка», «устаревшее» — рубрика
**e1c.3** = e1c.2 + правило из проверки Егора (L01): обоснованная приоритизация блокирующего
вопроса на «связать» засчитывается. Рубрику заморозить до прогона.

**Защита:** у V9 «выдумка» не выше V9-control более чем на 5 п.п.

**Стоимость:** вызовы и токены на вопрос по вариантам.

## 4. Модели

- **Отвечающий — сильная модель.** Кандидаты: GLM (NVIDIA, раньше зависал), DeepSeek V4.1
  Flash, Nemotron-3 Ultra **с** рассуждениями. Проба 5 вопросов на каждого: задержка,
  зависания, держит ли протокол шагов. Отчёт и выбор — у Егора.
- **Судья — не та же модель, что отвечает.** Если отвечает DeepSeek — судья другой (записать).
  Второй судья на 20 % + κ, как в E1c.

## 5. Порядок

1. **Этап A, без API.** Реализовать рукава, пересечения, якорь, V9-q. Тесты (pytest, ruff).
   Посчитать полноту V9-q против V6 на всех 200 вопросах по типам → таблица Егору.
   Пометка: разведка (до пре-регистрации V9). Порог якоря тут не подбирать на основных
   вопросах — использовать пробные.
2. **Этап B.** Протокол шагов, V9-control и V9. Тесты на протокол с заглушкой модели.
3. **Этап C.** Проба моделей-отвечающих (5 вопросов каждая) → выбор Егором.
4. **Пре-регистрация `prereg_e1d.md`** (варианты, модель с версией, бюджеты, параметры
   рукавов/бонуса/порога, метрики, тесты, критерий успеха) → коммит.
5. **Этап D, пилот:** 20 вопросов «связать» × 3 варианта (V9-control, V9, V6). Проверить
   полноту и что протокол держится. Если полнота V9-control < 15 % и у V9 не выше — стоп,
   обсуждаем.
6. **Этап E, полный прогон:** 200 вопросов × 4 варианта. Оценка числа вызовов и стоимости —
   до запуска, ждать «да».
7. Отчёт `result_e1d.md`: главное сравнение, сетка 2×2, по типам, стоимость, 3–5 примеров
   «V9 нашёл факт, которого не было у V9-control» с текстом шагов и рукавов.

## 6. Чего не делать

- Не менять сжатие и окно между вариантами.
- Не подбирать параметры на основных 200 вопросах после пре-регистрации.
- Не включать «актуально», сокращения, закрепление.
